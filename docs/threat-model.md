# Bayplan threat model (Phases 1 to 4)

This describes what Bayplan protects against in its first four builds (install, sign-in and a read-only view of the local Docker host in Phase 1; remote hosts and swarms through agents in Phase 2; users, teams, roles, encrypted backups, restore and key rotation in Phase 3; changes to containers, networks and volumes, logs and shells in Phase 4), what it does not, and the risks that remain. Threat IDs (T-01-nn to T-04-nn) refer to the plans in which each mitigation was designed and tested.

Phase 4 widens what an agent forwards: container actions, logs, shells, and network and volume changes. This revision covers Phase 4 in "What Phase 4 adds" and in residual risks 10 and 25 to 28, with the Docker access rows in the boundary table; the end-to-end proof of Phase 4 is in "What Phase 4 adds" as well.

## The headline

**Bayplan server compromise == root on every managed host.**

Bayplan manages Docker through the Docker API, and the Docker API is root-equivalent. A process that can talk to `/var/run/docker.sock` can start a privileged container that mounts the host's root file system, read any file, and change any setting. So whoever controls Bayplan controls every host it is connected to, whatever the individual buttons in its interface allow.

Three consequences follow, and the README repeats them before the install command (T-01-116):

- Mounting the socket is a decision about the host, not about an application. Do it only on hosts you intend Bayplan to manage. Nothing is managed until an admin opts in after setup, and the opt-in screen says the same.
- Every admin account is a root account on the managed hosts. Treat admin passwords, sessions and the machine that runs the browser accordingly.
- The strength of Bayplan's defences matters less than its exposure. Do not publish port 7480 to the internet. Put it behind TLS and, if you can, behind a network boundary or VPN.

Phase 2 adds remote hosts through agents, which widens the same statement to **every host with an agent**. Since Phase 4 an agent forwards changes as well as reads (see below): a Bayplan that is compromised can stop, kill and remove containers, open a shell in any running container, read container logs, and create and delete networks and volumes on every host whose agent is not read-only. A shell in a privileged container, or in one that mounts the Docker socket or the host's file system, is root on that host, so the headline holds through agents too. The agent's fixed route table still keeps a compromised Bayplan from creating containers, services or images, so it cannot start the classic privileged container itself.

## Trust boundaries

| Boundary | What crosses it | Main controls |
|----------|-----------------|---------------|
| Browser to API | Sign-in, sessions, every change the UI makes | Server-side sessions, CSRF token, Origin check, strict CSP, per-route permission policy |
| Internet to setup and sign-in | The setup token, passwords | Setup token gate, rate limits, account lockout, one error for every sign-in failure |
| Bayplan to the Docker socket | Every Docker API call | Typed facade with a pinned method set (reads plus a closed set of container, network and volume changes, no create of containers, services or images and no passthrough), per-permission and audited write endpoints, `unix://` only, privilege drop to UID 1000 |
| The `/data` volume | The database, the master key, the setup token file, the TLS key | File modes 0600, ownership by UID 1000, key never logged, backups documented |
| Reverse proxy to Bayplan | Client addresses, scheme | Forwarded headers believed only from `BAYPLAN_TRUSTED_PROXIES` |
| Agent to Bayplan, `/agent/connect` | The join token (once), the agent's signed challenge, every Docker answer, update and uninstall messages | Verified TLS, per-environment CA and key-based authentication inside the tunnel, handshake limits, throttled audit of refusals |
| Bayplan to an agent's Docker socket | Docker requests Bayplan sends over the agent's tunnel | The agent's own route table (method, path, query keys and a rebuilt body for each call), its 64 KiB body cap and its read-only flag, all enforced on the host |
| Signed-in users of different roles to the API | Every request for an environment or an administrative action | One permission registry, a role matrix generated from it, 404 for environments the caller has no access to, refusals audited and coalesced |
| An environment Admin to the people and teams of an instance | Giving, changing and removing access on one environment | Delegation capped to that environment and to Admin, Operator or Viewer; instance admins and all-environments access out of reach |
| The holder of an invite or reset link to Bayplan | A bearer token that sets a password | One-time, expiring, hashed at rest, in the URL fragment, never signs in, one answer for every dead link |
| A backup file outside Bayplan | Every user, hash, certificate authority and audit entry | A passphrase-derived key and an authenticated cipher, no master key inside, the passphrase never a flag |
| The offline command line on `/data` | `restore`, `key rotate`, `backup`, `user reset-password` | Runs as UID 1000, takes the data-directory lock, validates before it changes anything, audited as `system:cli` |
| The build pipeline | Source, dependencies, the two images (`bayplan` and `bayplan-agent`) | Pinned actions, licence gate, minimum release age, digest-pinned base, signatures and SBOM on both images |

## What Phase 1 builds in

**Docker access is narrow and typed (T-01-64, T-01-65, T-01-66; widened in Phase 4 by T-04-01 to T-04-05).** All Docker calls go through one package, `internal/dockerx`, and a lint rule keeps the Docker client out of every other package. The package exports typed methods only, none of which takes or returns a Docker library type, and a reflection test pins the exact method set. A pattern in the same test refuses names in the write and passthrough families (create, remove, start, stop, kill, exec, update, prune, raw, passthrough, plugins, swarm init/join/leave/unlock); each Phase 4 method that has to carry such a word is listed and reviewed by name. `DOCKER_HOST` accepts `unix://` paths only, and the environment never chooses the API version or TLS settings. Engines Bayplan does not support (older than Docker 24, rootless, Docker Desktop, Podman) are detected and refused with a reason rather than treated as supported (T-01-80). Since Phase 4 the facade also changes things, through a closed set of calls; that is described in "What Phase 4 adds".

**Default-deny authorisation (T-01-04, T-01-29, T-01-30, T-01-31, T-01-34).** Every route declares a requirement. Registering one without a requirement panics at startup, and a startup check walks the router to prove each route is guarded. The policy engine denies anything not explicitly granted, resolves the environment before the permission check, and writes an audit entry for every denial; if that write fails the request fails. Hiding a control in the UI is only convenience (T-01-58): the server decides.

**Sessions and CSRF (T-01-44, T-01-52, T-01-53, T-01-33, T-01-57).** Session IDs are 256 random bits and only their SHA-256 is stored. The cookie is `HttpOnly` and `SameSite=Lax`, and `Secure` with the `__Host-` prefix when the public URL is `https`. A new session is created at sign-in. Every state-changing request needs an `X-CSRF-Token` derived from the session with a key held in the vault, compared in constant time, and an `Origin` that matches the public URL. Only the cookie of the configured scheme is read: on an `https` instance the bare cookie is ignored, so one planted from a sibling host or over plain http cannot stand in for it (T-01-G07), and changing the public URL scheme signs browsers out once. Sessions end after 12 hours idle, remembered sessions after 30 days, and sign-out deletes the server-side row. Open event streams were authorised only when they opened, so they are re-checked on every 15-second heartbeat (session, user, environment and permission, without touching the session) and capped at one hour. Sign-out, a password change that ends other sessions, idle expiry, a disabled user, a removed or disabled environment or a withdrawn permission therefore ends a stream within a heartbeat, and the browser's reconnect gets a 401 (T-01-G08). The sign-in `next` parameter only follows same-origin paths.

**Sign-in hardening (T-01-50, T-01-51, T-01-42, T-01-43, T-01-45, T-01-60).** Passwords are argon2id (m=19456 KiB, t=2, p=1, per-hash salt), at least 12 characters, checked against an embedded common-password list and against the user name. Five failed sign-ins lock an account for 30 minutes, and there is a per-address limit. Unknown, disabled and wrong-password cases give one error and one status, and unknown users still pay the hashing cost. Hashing is limited to four at a time. Changing a password needs the current one, is throttled per user, ends other sessions and is audited.

**The setup token gate (T-01-36, T-01-38, T-01-39, T-01-40, T-01-41, T-01-46).** An unclaimed instance has a 128-bit token, compared in constant time, with a per-address limit, and every failure is audited with the address. Once an admin exists the setup endpoints answer 409. Completion re-checks the user count inside the write transaction, so two simultaneous attempts cannot both win. There is no development or configuration switch that skips the gate (T-01-09).

**Audit log (T-01-23, T-01-25, T-01-27, T-01-28, T-01-98, T-01-99).** Every entry is chained with an HMAC keyed from the master key, which is not stored in the database, so rows edited or deleted from the middle are detectable with `bayplan audit verify`. Appends happen in one immediate transaction, so concurrent writers cannot fork the chain, and a failed append fails the request instead of dropping the entry. Detail fields cannot carry secrets, and lengths are capped. Only admins can read the log, and exports leave out the chain internals. CSV exports neutralise formula-looking cells (T-01-97, T-01-103).

**Secrets at rest (T-01-15, T-01-24).** The master key is 32 random bytes, in `/data/bayplan.key` (mode 0600, written atomically) or in `BAYPLAN_ENCRYPTION_KEY` / `BAYPLAN_ENCRYPTION_KEY_FILE`. It is never logged, never in the database and never returned by an API; only derived subkeys are used. Settings are logged with secrets redacted.

**Running unprivileged (T-01-108, T-01-109, T-01-112).** The container starts as root only to fix the ownership of `/data` and join the socket's group, then becomes UID and GID 1000, in every subcommand, so the command-line tools never leave root-owned database files. The base image is distroless, with no shell. The self-signed TLS key is written 0600 under `/data/tls`.

**Browser hardening (T-01-03, T-01-05, T-01-06, T-01-113, T-01-114).** The Content-Security-Policy is `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; ...; frame-ancestors 'none'`, plus `nosniff` and `Referrer-Policy: no-referrer`. Fonts are bundled and nothing loads from another origin. The one concession is inline styles, which the toast library needs (T-01-63); scripts stay `'self'`. The end-to-end suite fails on any CSP violation and on any request to another origin. That check found, in Phase 4, that the form-validation library probed `eval` on every page before it had been told not to; every module now takes it from one place that turns the probe off first, so the policy needs no `unsafe-eval`. All strings from Docker, users or the audit log are rendered as text, never as HTML (T-01-48, T-01-59, T-01-81, T-01-84, T-01-91, T-01-101).

**Data safety (T-01-18, T-01-19, T-01-20, T-01-21, T-01-22, T-01-61, T-01-62).** Migrations are transactional and preceded by a snapshot with a free-space guard; a database from a newer schema refuses to start. A `/data` that is not a mount, or is tmpfs, is warned about, and the key-backup reminder is acknowledged in the audit log. All SQL is generated with bound parameters.

**Availability controls (T-01-17, T-01-54, T-01-71, T-01-79, T-01-87, T-01-90).** The HTTP server has header (10 s), read (30 s) and idle (120 s) timeouts, so a client that sends headers and withholds the body is cut off; the read timeout ends when a bodyless request is being served, so the events stream is not affected, and there is no write timeout. A locked-out sole admin has `bayplan user unlock`. Probes of a dead daemon back off, and a slow resource listing never holds up a probe, so a busy but healthy engine is not reported offline. The self-signed certificate is kept across container recreation, renewed before it expires, and never pinned with HSTS, so an upgrade cannot lock a browser out. Resource lists are capped and cached. Each principal gets at most eight event streams, and one daemon stream serves any number of viewers.

**Opt-in management (T-01-69, T-01-74).** The local host becomes an environment only through an explicit request by an admin, after the root-equivalence notice, and the change is audited.

**Supply chain (T-01-08, T-01-11, T-01-12, T-01-13, T-01-14, T-01-111).** Packages younger than 24 hours are refused by pnpm; the lockfile is committed and installs are frozen. A licence allowlist (Go on both architectures, and production npm packages) fails the build on anything else, and exceptions need a written reason. CI actions are pinned to full commit SHAs with read-only tokens and no secrets. Commits need a DCO sign-off. Release images use a digest-pinned base, keyless cosign signatures and an SPDX SBOM, and there is no `:latest` tag (T-01-76).

## What Phase 2 adds

**The agent connection is a new trust boundary, `/agent/connect`.** It is a WebSocket that anyone who can reach Bayplan can open, so it is hardened before any authentication: only `wss://` is accepted unless the development switch is set or the agent address is on Bayplan's own machine (loopback), which no other host can be told to dial, the `Origin` header must be absent (a browser sends one), at most 64 handshakes run at once and at most 16 of them from one client address (an IPv6 /64 counts as one address, and a forwarded address counts only when it comes from a trusted proxy), an agent that does not answer the challenge within 3 seconds is dropped, each address has an attempt budget, the warnings logged before admission are written at most once per address per minute (T-02-24), and a busy server answers `rate_limited` inside the protocol so a well-behaved agent waits. The refusals from a flood go through an audit throttle of their own (20 rows per address, then one per six seconds, then a counted summary), so a flood cannot starve the single database writer and still leaves a count. Only a peer in `BAYPLAN_TRUSTED_PROXIES` can make a connection count as `https` by sending `X-Forwarded-Proto`; the end-to-end run proves both sides: through a trusted proxy the agent connects, and without it Bayplan refuses with "did not arrive over TLS".

**Each environment has its own certificate authority, and agents authenticate with a key, not a shared secret.** The join token enrols a host once. The agent generates a key pair, proves possession of it by signing a challenge that is bound to the TLS session where the proxy allows it, and receives a certificate from its environment's CA, valid for 30 days and renewed over the live connection two thirds of the way through. After that the token is not used. Rotating or disabling the token never disconnects an enrolled agent, and revoking one agent never affects another. A compromised agent key gives access to that one environment's connection and nothing else; the CA key of an environment is stored sealed under the master key and opens only for its own environment. A hello whose certificate the environment's CA did not sign gets the same `auth_rejected` answer whatever its dates, so a forged certificate cannot tell whether an environment exists; only a certificate the CA issued is told it expired (T-02-21).

**On `wss://` the agent verifies Bayplan and never skips the check, and it does not dial plain `ws://` to another host unless `BAYPLAN_AGENT_ALLOW_INSECURE=true` is set on the agent (T-02-31 to T-02-34).** Only the install commands of a Bayplan that runs the development switch carry that setting, and only for a `ws://` address; stored addresses follow the same rule, and addresses Bayplan pushes are taken only as `wss://` over a verified session. Bayplan itself never hands out a plain agent address for another host without the switch: adding an environment, rotating a token, saving such an agent URL, the manual update command and the update hint all refuse it or leave it out (T-02-139, T-02-144, which replace the accepted T-02-137). Over `wss://` the agent trusts a certificate from the system's public CAs, or the pin of Bayplan's own self-signed key, or the pin of a certificate or certificate authority that the operator names with `BAYPLAN_AGENT_PIN` for a proxy with a private certificate. A pin only adds trust, a pinned authority counts only when the certificate presented chains to it for the address dialled, and there is no setting that turns verification off. Pins and new addresses that Bayplan pushes to an agent are accepted only on a session whose TLS was verified.

**The agent forwards a fixed table of calls, and the host owner can make it read only (T-04-06 to T-04-12, T-04-16).** Phase 2 gave the agent a table of reads; since Phase 4 it also holds a closed set of changes. The table, how bodies are rebuilt, what is refused whatever Bayplan asks, and the read-only flag are described in "What Phase 4 adds".

**Self-maintenance is the agent's only write, and it is narrow (T-02-88, T-02-90 to T-02-92).** Bayplan can ask an agent to update or uninstall itself. The agent accepts only an image from its own repository, only on a session whose TLS was verified (otherwise `insecure_session`), and only when the host owner has not set `BAYPLAN_AGENT_SELF_UPDATE=false`. A swarm update is Docker's rolling update of the agent's own service; a standalone update runs a short-lived helper container that recreates the agent with the same configuration and rolls back if the new container does not start. Automatic updates stay inside the compatibility window and a failed automatic update is not repeated for the same image. Every update and uninstall is audited under the admin or `system:agent-update`.

**Join tokens and CA keys at rest.** A join token is stored as a hash, never in the clear; a raw-byte search of the whole data directory after a real enrolment and rotation finds no join token, no secret part and no CA key (with a negative control that plants them). The token is shown once, in the install command, whose values are checked before they are quoted into a shell line or a YAML file (T-02-36) and which starts with a space so shells that skip space-prefixed lines keep it out of history. On a swarm it is held in a Docker secret. On a standalone host it is an environment variable of the agent container and so visible in `docker inspect` until the token is rotated.

**The session cookie is scoped to the base path (T-02-11).** Behind a subpath over `https` the cookie is `__Secure-bayplan_session` with `Path=/bayplan`, so another application on the same host does not receive it, and the end-to-end suite checks the name, path, `Secure`, `HttpOnly` and `SameSite` through a real proxy. The base path, host and origin come from the public URL only: `X-Forwarded-Host` and `X-Forwarded-Prefix` are never read.

**Proxy mistakes are noticed, not ignored (T-02-80 to T-02-82).** Bayplan records forwarded headers from an untrusted peer, requests whose host or scheme is not the public URL's, and agent upgrades that fail, and shows each as a bell item to admins who can read settings. It holds the sightings for an hour and at most 256.

**The end-to-end harness is built to be safe (T-02-100, T-02-101).** Its two privileged Docker-in-Docker containers and its throwaway admin are published on `127.0.0.1` only, with a seven-day certificate under `.devdata`. `docs/agent.md` labels `BAYPLAN_AGENT_ALLOW_INSECURE` as development only and never suggests turning verification off.

## What Phase 3 adds

**Roles are enforced by the server on every request, and the interface only follows (plan 03-05).** Access is the union of a user's own entries, their teams' entries and any all-environments entry, with no deny rules, evaluated on every request, so a removal takes effect on the next call and open streams for the environment are closed within a heartbeat. The role matrix is generated from the permission registry (`docs/permissions.md`), and an enforcement test drives every environment route as every kind of user (instance admin, Admin, Operator, Viewer, no access, disabled) and checks the answer against rules written independently of the code under test.

**An environment the caller cannot see is `404 environment_not_found`, like one that does not exist.** The visibility step runs before any environment lookup, so a user cannot tell a hidden environment from a missing one, and a disabled environment answers 409 only to people who have access to it. The refusal is still audited, with the reason that the environment was not visible. The one self-service route that takes an environment ID, recording a use (`PUT /api/me/recent-environments/{envId}`), answers and audits the same way, through the same coalescer, so probing IDs through it leaves the same trace and cannot flood the log. Instance admins are the only role that holds global permissions; no environment role grants one.

**Delegation cannot launder privilege (D-11, D-12; plan 03-20).** Only instance admins create users and teams or change who is in a team, and the instance-admin flag cannot be given through a team. An environment Admin gives access on their own environment only. The route they use has no scope field to abuse, and a crafted request that names an instance admin, another environment or an all-environments entry answers `403 delegation_denied` and is audited. The last active instance admin cannot be demoted, disabled or deleted, and the server counts after the change inside the transaction.

**Refusals are audited without letting a client flood the audit log (D-20; plan 03-10).** The first refusal for each user, action, reason, target and environment is written in full and synchronously, so a failed write still fails the request. Identical repeats within 60 seconds cost a counter and are written as one summary row, and ten or more in a window raise a bell item for instance admins. A table of open windows is bounded, and a full table writes through rather than dropping.

**Invite and reset links are bearer tokens, and are handled as such (D-22; plans 03-11, 03-15).** They are 256 random bits, stored only as a hash, valid once and for 72 hours by default, and placed after a `#` so they are not sent to Bayplan or a proxy in the request. The page moves the token into memory and removes it from the address bar before it renders. Accepting a link never creates a session, so a leaked link does not sign anyone in: it only lets someone choose that account's password, which is why the dialog tells the admin to send it privately. Regenerating a link or issuing a reset replaces the earlier one, a reset ends the user's sessions, every refused link is audited as `auth.link_refused` (rate limited), and the page gives one answer for expired, used, replaced and unknown links.

**Deleted users leave a tombstone (D-22c).** The username is reserved for ever, so audit entries keep their meaning and nobody can take a former user's name. Disabling a user ends their sessions and keeps their access, so enabling restores them.

**Automations run as their owner, rechecked every time (D-14; plan 03-13).** A git sync or webhook runs as a system principal on behalf of the user who set it up, against that user's current permissions. If the owner is disabled, deleted or has lost access, the run is refused, the automation pauses visibly, and an entry is written. Ownership moves only to a user who holds enough access, checked live, and an automation is never created with more rights than its owner has.

**Compose files that reach the host need an Admin (D-13, AUTH-10; plan 03-06).** The checker reads the compose file with a work budget (a hostile file cannot make it spin), reports the offending key and line, and treats any value it cannot resolve as unsafe. It flags `privileged`, added capabilities, devices, shared host namespaces, the host network, disabled confinement, and bind mounts of the Docker socket, runtime sockets and host roots. It errs towards flagging. The stack screens that call it arrive in later phases; the policy hook is in place now.

**Backups are encrypted, self-contained and never carry the master key (D-28, D-29; plans 03-02, 03-16).** The file is encrypted with a key derived from the passphrase by argon2id under an authenticated cipher, and every stored secret is re-encrypted for the file, so the master key is not in it and the file restores onto an install with a different key. The format carries a version and its parameters. The passphrase must be at least 16 characters, and it is never a flag or in the audit log. Sessions, invite and reset links and pending join tokens are left out. A test fails if any table is not classified as included or excluded.

**Restore is validated, staged and reversible (D-30; plans 03-16, 03-25).** The file and passphrase are checked, and the backup is migrated and re-keyed on a private copy, before the data directory changes. A newer backup is refused. The current database is saved first as `prerestore-<time>.db` (newest three kept), the swap removes the live write-ahead log before the rename, and a restore from the web interface rolls back to the snapshot when the restored database cannot start. The interface asks for the instance name and takes only instance admins. The audit chain is re-keyed under the new master key with a signed `audit.reanchored` entry saying where it came from, and `bayplan audit verify` passes afterwards. The upload is size-limited (`BAYPLAN_BACKUP_MAX_UPLOAD`), and only one is held at a time.

**Offline commands take the data-directory lock (plans 03-16, 03-18).** `restore` and `key rotate` refuse while a server holds it, and the refusal creates nothing: no key file, no staging directory, no snapshot.

**Key rotation is crash-safe and does not print the key (D-33; plan 03-18).** The new key is written 0600 and never shown. The old key is kept as `bayplan.key.old` and vouches for a `key.rotated` entry, so the re-signed chain can still be checked. An interrupted rotation is finished or discarded at the next start, and a stray `bayplan.key.new` is never taken as the master key on its own. A start whose key is not the database's active key is refused, rather than splitting the data across two keys. With a key from `BAYPLAN_ENCRYPTION_KEY` the new key goes to a file for the operator to apply.

**Scheduled backups are bounded (D-32; plan 03-27).** The schedule writes into one configured folder, and retention deletes only files that match `bayplan-backup-YYYYMMDD-HHMM.bayplan` in it. A backup made by hand with `bayplan backup` and no `--out` goes to the same folder under a different name (`bayplan-manual-YYYYMMDD-HHMMSS.bayplan`, never given to a file that exists), so retention neither counts nor deletes it and it cannot replace a scheduled one; the Backup page does not list or serve it. A failed run raises a bell item for instance admins. The schedule's passphrase is stored sealed under the master key.

**Agents after a restore (D-31; plan 03-28).** The environments' certificate authorities come back with the backup, so agents enrolled before it reconnect. An agent enrolled after it presents a certificate the restored database has no record of and is refused as `unknown_agent`, not trusted. The list of refused agents is in memory only, bounded, and aged out after 24 hours, and showing an install command makes a fresh token.

**The end-to-end suite proves the story in a browser (T-03-120).** An invited user, given Viewer through a team, sees one environment read only; another environment is "Page not found"; a direct API call for a hidden action answers 403 and appears in the audit log; and a backup is downloaded and restored over the running instance. These run on every pull request.

## What Phase 4 adds

Phase 4 is the first phase in which Bayplan changes Docker, so most of this section is about what is allowed, who may ask, what is recorded and what is kept out of a browser. The paragraphs cover, in turn, Bayplan's own Docker access, the agent's route table and read-only flag, the browser shell, masking, stream limits, logs, the Events page, and the proxy smoke test.

**Bayplan's own Docker access also changes things, through a closed set of typed calls (T-04-01 to T-04-05, T-04-22 to T-04-28).** Phase 1 was read only. Since Phase 4 the facade also changes things, through the same closed set of calls an agent forwards (see below):

- **Containers:** start, stop, restart, kill, pause and unpause, from a fixed set of verbs, with a stop timeout and a signal; and remove, with force and the container's anonymous volumes as the only options.
- **Networks:** create (bridge, overlay, macvlan and ipvlan only, with no way to ask for an ingress, config-only or config-from network), connect a container with only an alias and fixed addresses, disconnect without force, and delete.
- **Volumes:** create, and delete without force.
- **Shell:** an exec with only a terminal, a user, a working directory and a command. It cannot be privileged or carry environment variables. The browser shell opens one for a holder of `containers.exec` (see the browser shell paragraphs below).

The facade has no method to create or change a container, service or image, pull an image, or send a raw request, so the API cannot reach one through Bayplan's code. Every write endpoint checks a permission per environment before it calls Docker: `containers.control` and `containers.remove` (Operator), `networks.connect` (Operator), `networks.manage` and `volumes.create` (Admin), and `volumes.delete` (an extra; removing a container's anonymous volumes needs it too). A bulk request names at most 25 targets. Each target is audited, failures included, and a write is never retried after a dropped connection. A row written after a change (a container action, a network or volume change, an administrator ending a shell) uses a context that outlives the request, with its own 10-second deadline, so a browser closed while the change ran cannot leave it without a record; the end-to-end suite found the gap for container actions and the fix was extended to the rest (plan 04-29). Bayplan's own server and agent containers can be stopped, killed, restarted, paused or removed only one at a time, with the container's name typed and checked on the server, and a bulk request skips them for those actions. Network and volume deletes re-read what uses them just before the call and refuse one still in use. **The local host has no read-only switch:** unlike an agent, the socket Bayplan mounts is managed through these endpoints by anyone holding the permissions above. Do not mount the socket on a host Bayplan should only watch; give that host an agent with `BAYPLAN_AGENT_READ_ONLY=true` instead.

**The agent's route table and the read-only flag are host-side defences (T-04-06 to T-04-12; the route tests, the independent fuzz oracle and the `FuzzBody` target in `agent/internal/proxy`).** The agent runs a reverse proxy in front of the Docker socket and checks every request against one fixed, ordered table of method, anchored path, allowed query keys with a pattern for each value, body kind and whether an upgrade is allowed. The agent decides from the bytes it receives, so a compromised Bayplan cannot widen the table. A request that is not in it gets a typed `agent_policy_denied` refusal, which the host's audit trail and Bayplan's audit log both record. The full list is in `docs/agent.md` ("What the agent forwards"). In short:

- **Reads:** ping, version, info, events, the four resource lists, the swarm lists, the inspect of one container, network or volume, the state of one exec, a container's logs (only the documented log keys), and volume disk usage.
- **Changes:** start, stop, restart, kill, pause, unpause and remove of a container (only the timeout, signal, `force` and `v` keys); create, start and resize of an exec; create, connect, disconnect and delete of a network; create and delete of a volume.
- **Bodies are rebuilt, not passed through.** Exec create and start, network create, connect and disconnect, and volume create are decoded strictly into Docker's own request types, compared with a value built only from the allowed fields, and forwarded as that fresh value. A body larger than 64 KiB or a query larger than 4 KiB is refused.
- **Refused whatever Bayplan asks:** a privileged exec, an exec with environment variables or detach keys, an exec without a terminal, and a detached exec start; any upgrade other than starting an exec (`attach` and the file `archive` are refused); ingress, config-only and config-from networks, drivers other than bridge, overlay, macvlan and ipvlan, and IPAM options; a forced disconnect; cluster volumes; `link` on a container remove and `force` on a volume delete; creating or changing a container, image or service; container stats, export and files; and `GET /swarm`, whose answer carries the swarm join tokens.

The host owner can set `BAYPLAN_AGENT_READ_ONLY` to refuse every request that is not a `GET` or `HEAD` before the table is consulted, so no shell can be opened and nothing can be changed, whatever a later release adds to the table. Bayplan reads the flag from the live session and refuses a change to such a host itself, as `host_read_only`, before it sends anything (T-04-16). An agent older than the server refuses the newer calls with `agent_policy_denied` until it updates. What a compromised Bayplan can still do through an agent is in residual risk 10.

**A browser shell is opened in two steps, so another site, another person or another sign-in cannot attach to it (T-04-76, T-04-77, T-04-81).** A browser cannot put a CSRF header on a WebSocket, and the router checks the CSRF token and `Origin` only on changing methods, so a shell is not one request. The first is a `POST` that passes both checks and needs `containers.exec` on the environment: it makes the exec and a pending session, and nothing is attached yet. The second is the WebSocket upgrade, which also needs `containers.exec` and claims that session. A session is single use, is bound to the user and to the hash of the sign-in session that made it, and waits 30 seconds for its browser, after which it is ended. A request for a session that is unknown, already claimed, expired, on another environment or bound to another user or sign-in gets the same 404, and the session is checked before the upgrade, so a request that the origin check refuses does not use it up. The upgrade is accepted only from the request's own host or the instance's public origin, scheme included, read on every request so that a change of the public URL applies at once (`OriginPatterns`, with the library's default origin check kept on). The option that turns that check off is never used, and the repository's TLS gate, `scripts/insecure-tls-check.sh` (run by `make lint`), fails the build when any Go file outside the one reviewed agent file names the setting that disables verification, which is also the name of the origin check's off switch. A shell is carried in 32 KiB writes with a 30 second write timeout, a 64 KiB read limit, a ping every 20 seconds and a resize limited to 1 to 1000 columns and rows (T-04-79); the connection's own deadlines are cleared, because a shell lives for hours, and the idle limit, the user's access and the server's shutdown end it instead.

**A browser shell is audited when it opens and when it ends, including when Bayplan stops (T-04-78, T-04-82 to T-04-88, T-04-94 to T-04-97).** Only the start and the end of a shell are recorded, never what is typed or printed; tests check the audit log, the server's own log and the page for terminal contents. `shell.opened` is written before the browser can attach, with the container, node, session, command, user, working directory and client address. If that write fails, the session is ended, so no shell runs that the log does not know about. `shell.closed` records how long the shell lasted, the exit code or that the process was left running, and why it ended. A server that stops tells every open shell's browser `server_shutdown` and does not finish stopping until each shell's `shell.closed` row is written. The HTTP server runs its shutdown hooks without waiting for them, so the graceful shutdown waits for every end in flight before the database closes; without that, a restart could lose the end of an open shell (fixed in plan 04-22 after its shutdown test caught it). A shell also ends, through the same audited path, when it has seen no input or output for the instance's idle limit (default 30 minutes, 5 to 240; the browser is warned a minute before and the limit is re-read on every check), with reason `idle`; and when its user no longer holds the shell permission, the grant on the environment or the sign-in, re-checked every 5 seconds, with reason `access_lost`. Some shells are refused before any exec is created, so they write no row: one on Bayplan's own server or agent container (decided from a fresh inspect, so Bayplan cannot cut itself off), on a read-only host, in a stopped container, through an agent too old to forward it, or beyond the per-user limit of open shells across environments (default 10). Only an instance admin can change the idle limit and the per-user cap, and each change is a `settings.updated` row. Every open shell is visible to whoever administers its environment: `shells.manage`, held by an environment Admin or an instance admin and never by an Operator or as an extra, lists each open shell on the environment with its owner's name, the container, the node, when it started and how long it has been idle (never what it shows or the command), and ends any of them. An administrator's end is two rows: `shell.ended`, with the administrator as actor and the owner, container, node and session named, and the owner's own `shell.closed` with reason `ended_by_admin`, so it cannot be done quietly. A person can list and end their own shells with the shell permission alone (`shell.closed`, reason `ended_by_user`); another person's session, another environment's session and one that has already closed all answer the same 404, even to an administrator on those routes. Both ends go through the same path as every other, so the shutdown wait above still holds. Bayplan remembers how each user last opened a shell in each image (the shell, a custom command, the user and the working directory) in `user_shell_prefs`, at most 200 rows per user, deleted with the user and carried in backups. It is meant to hold no secret, but a custom command is stored as typed, as it is in the `shell.opened` row, so do not put a password on a shell's command line. Closing a shell closes the terminal attach only: a process the user left running in the container keeps running (T-04-80, accepted), and its `shell.closed` row says so.

**Values that can hold credentials are masked on the server, and only `secrets.reveal` lifts the mask (T-04-40, T-04-111, T-04-59, T-04-70, T-04-55).** The container page, its raw Inspect JSON, the volume page and its raw Inspect JSON, and the notice for a log that Docker cannot read back all send values through one package. The values of a container's environment variables and of its log driver's options, and the values of a volume's driver options (which, for an SMB or NFS volume created from Bayplan, can hold the share's password), are withheld unless the caller holds `secrets.reveal` on that environment: an Admin, an instance admin, or an Operator granted it. The names stay and the value, not even its length, is sent, and a raw document that cannot be read as a JSON object is an error and never passed through, so a malformed answer cannot carry a value past the mask. The audit row for a volume create records the options it was asked for with password-like names and segments replaced, and cuts the text at 500 bytes after masking, so no row holds a share password. What is not masked is in residual risks 26 and 27. Docker itself keeps a volume's options in clear on the host, so the mask protects the browser and the audit log, not someone who can run `docker volume inspect`; the create dialog says so.

**Streams are capped per person and per agent, and end when access ends (T-04-13, T-04-14, T-04-65, T-04-66, T-04-72, T-04-79, T-04-86, T-04-87).** A person may hold 8 live log streams (the ninth answers 429), two log downloads at once (429), and by default 10 shells across all environments (429 `shell_limit_reached`; an instance admin can set 1 to 50, and the cap is asked before anything is read from the engine and again under the registry's lock). A log stream lives at most an hour and is re-authorised every 15 seconds, and a shell is re-authorised every 5 seconds and closes after the idle limit, so a person who loses the permission, their grant or their sign-in loses the stream or shell within seconds. A download is copied through one fixed 32 KiB buffer a line at a time, so a log of any size costs the server no more than that, a single log line is cut at 256 KiB, and a page of earlier lines is limited to 8 MiB. Each agent session carries at most 64 server-opened streams, and at most 32 of those may be container log reads or shells; the other 32 stay for reads, actions and the events feed, so a crowd of log viewers cannot starve the dashboard or other people's actions. A request over the budget is refused at once with 503 `stream_busy` and never queued. Which requests are streams is decided from the request line that the server itself wrote, never from anything the agent sends; every other answer keeps the 64 MiB cap. These per-agent caps apply to agent sessions; the local socket has no tunnel. The caps for event streams are in the Events paragraph below.

**Opening or downloading a log is audited, and the lines are never kept (T-04-63, T-04-64, T-04-73).** `logs.viewed` is written once for each viewer window (the viewer's `sid`) with the container, node, how many lines and since when, so a browser that reconnects writes nothing more, and a new `sid` always writes a new row, which is more audit and not less; if the table that remembers the `sid`s is full, the row is written anyway. `logs.downloaded` is written when the response starts, with the container, node, the end of the range, the start if one was given and whether timestamps were asked for. Neither row holds a line of the log, and a test proves that a marker line written by a container reaches neither the audit log nor the server's own log. Unlike a shell's start, these rows are not a condition: if the write fails, the error is logged and the person still gets the log. A container whose log Docker cannot read back writes no row, because nothing was shown. The lines themselves are shown as the application wrote them and are never masked (residual risk 26).

**The Events page shows only an allowlist of each event's attributes, and keeps nothing (T-04-98 to T-04-104).** Docker puts every container label into an event's attributes, and for some events an environment value or a command line, so Bayplan passes on only twelve named keys: `name`, `image`, `exitCode`, `signal`, `type`, `container`, `driver`, `reason`, `destination`, `read/write`, and the two grouping labels `com.docker.compose.project` and `com.docker.stack.namespace`. No other label, environment value or free-form attribute reaches a browser, and a test pins the list. A container's `health_status` change, whose attributes can name the check command, is sent only as a refresh signal with no attributes and never appears in the feed, and the `exec_` events every health check and `docker exec` fire are dropped. What can still appear is an image reference (which can name a private registry), a mount's destination path, a container ID and a network's type and driver; on a swarm, service, node, secret and config events show their name and action only (T-04-101, accepted). The page and its feed need `environments.read` on the environment, which every Viewer holds, the same permission as the dashboard's feed; an environment the person cannot read answers as not found. Events are held in memory only: the server keeps the last 1000 per environment from at most the last 24 hours and loses them on restart, the tab keeps at most 1000, nothing is written to the database or the browser's storage, and viewing is not audited. The filters live in the URL, so a shared link carries the search text but no event data. Each stream is re-authorised every 15 seconds, lives at most an hour, and a user may hold eight event streams (a tab on the Events page holds two); a subscriber more than 64 events behind is dropped rather than buffered. Every value is rendered as text, never as markup, and links are built from route parameters, never from an attribute (T-04-102). Docker itself keeps only about its last 256 events and none across its own restart, so older history cannot be recovered.

**The proxy smoke test shows that each documented proxy carries the shell's upgrade and a log stream request to Bayplan, and no more (T-04-106).** `scripts/proxy-smoke.sh` runs the built image behind Caddy, nginx and Traefik, with the files in `docs/proxy`, at the root of a host and at `/bayplan`, and adds two checks for the correct setup (not for the deliberately broken nginx files). `shell_ws_reaches_bayplan` sends the upgrade request of a browser shell (`Connection: Upgrade`, `Upgrade: websocket`, a key and version, the session cookie and the public `Origin`) for an environment that does not exist, and passes only when the answer is a 404 whose JSON body is Bayplan's own `environment_not_found` problem. That shows the proxy forwarded the request, with its path under the base path, its cookie and its headers, to Bayplan, and did not answer 400, 426 or 502 itself. It does not show that a `101` upgrade completes or that terminal bytes flow. `log_stream_prompt` asks for a log stream of the same missing environment, with the session, and passes only when Bayplan's own JSON 404 comes back within 3 seconds. That shows the proxy does not hold a response to a stream request back. It does not stream a real log line, so it does not show that streamed lines are unbuffered; the script's existing check of the event stream's first frame does that for the one stream it opens. Neither check needs a container or a Docker socket. A real shell and real log lines through a proxy are covered by the end-to-end suite, in Chromium behind Caddy at `/bayplan` (see below); behind nginx and Traefik there are only these two request-level checks.

**The end-to-end suite proves Phase 4 in a real browser, through the proxy at a subpath, against a real engine (T-04-110).** It runs in Chromium against Bayplan behind Caddy at `/bayplan` over TLS, with a real Docker engine. Every test fails on any Content-Security-Policy violation or any request to another origin, and every address is under `/bayplan`. The Phase 4 tests, each passed in the full run (31 passed, none failed or skipped) and in three further runs of the Phase 4 project, plus one with HTTP/1.1 forced:

- A container started outside Bayplan appears in the list without a reload; it is stopped from its row through the confirmation dialog and started again, and two containers restarted together are both restarted in the engine, under one notice.
- The Logs tab streams stdout and stderr live with stderr marked, searches, downloads a file containing the lines, and pops out to a window that receives new lines at the same time as the tab; each page holds exactly one log stream.
- A shell opened from the Shell tab runs a command in the container: the file it creates exists in the engine and its output comes back over the WebSocket, whose upgrade was answered `101` at `wss://…/bayplan/…`, with the socket still open and no CSP violation. The policy's `connect-src 'self'` covers the `wss:` socket of the same origin, so the shell needs no wider policy (research question A4; observed in Chromium only).
- The Events page lists the container's `start` event.
- A network is created, joined with an alias, refused deletion while a container is attached, and deleted once empty; a volume is created and deleted only after its name is typed. Both are gone from the engine afterwards.

A tab on the Logs page holds three event streams and its pop-out one more, four in all, which stays within a browser's six connections per host even over HTTP/1.1 (research question A3); two Logs tabs over HTTP/1.1 would reach the limit (inferred, not measured). These tests do not check permission refusals, audit rows or masking, which the server's own tests cover. Not run: Firefox and WebKit, nginx and Traefik in the browser suite, a swarm environment and an older engine.

## Residual risks

These are known, accepted, and not hidden. 1 to 9 date from Phase 1, 10 to 17 from Phase 2 and 18 to 24 from Phase 3. Residual risk 10 was rewritten in Phase 4 for logs and shells, and 25 to 28 are new in Phase 4.

1. **Audit tail truncation is undetectable without an external anchor (T-01-26).** The HMAC chain proves that entries were not edited or removed from the middle. Someone who can write to the database can delete only the newest entries, which leaves a valid, shorter chain, and `bayplan audit verify` will still pass. Detecting that needs the head of the chain recorded somewhere an attacker with the volume cannot reach, such as a SIEM; streaming the log out is deferred.
2. **The setup token is visible to anyone who can read the container log or `/data` until setup completes (T-01-37).** It is printed and written to `/data/setup-token` (mode 0600, deleted at completion) by design, so that you can claim the instance without a prior secret. Anyone who has log or volume access already has host admin, but a shared log pipeline can widen that audience. Claim the instance as soon as it starts.
3. **Plain HTTP exposes credentials (T-01-110).** Bayplan serves HTTP unless you configure TLS or a TLS-terminating proxy, and it warns when it does. Passwords and session cookies then cross the network in clear text. First-class reverse-proxy support is planned for a later phase; this build supports `BAYPLAN_TRUSTED_PROXIES` and an `https://` public URL.
4. **The master key sits on the data volume, so a backup of the volume holds both the key and the data it protects.** Encryption at rest therefore defends against a copy of the database file alone, not against a copy of the whole volume. Keep backups protected, or supply the key through `BAYPLAN_ENCRYPTION_KEY_FILE` from a separate store and back it up separately. Losing the key loses the stored secrets and the ability to verify the audit log (T-01-119).
5. **Everything an admin can do, an attacker with an admin session can do (the headline).** Phase 3 narrows who is an admin: an instance admin, or an Admin on one environment, and Operators and Viewers can do less. But an instance admin, and an environment Admin on that environment's hosts, still holds root-equivalent control there, and there is no second factor. Bayplan limits damage with short idle timeouts, lockout and an audit trail; it cannot make an admin session less powerful than the socket it holds.
6. **Single-instance by design.** There is one SQLite writer and no high availability. A compromised or lost instance is recovered from backups.
7. **Inline styles are allowed by the CSP (T-01-63).** A style-injection bug would be easier to exploit than under a fully strict policy. Script injection stays blocked.
8. **Audit growth from scanners (T-01-35) and large exports (T-01-100)** are accepted: every denied read is audited, retention bounds the size, and exports stream from a read connection in batches. Repeated anonymous refusals from one address (denied routes, setup attempts after setup, rate-limited sign-ins) are written individually up to a per-address budget, 20 at once and then 10 a minute, and the rest as one summary entry per minute with a count, so a flood cannot starve the single database writer and every refusal is still recorded. Failed sign-ins that reach the account checks and wrong setup tokens are always written one row each.
9. **The CI end-to-end job runs a privileged Docker-in-Docker container (T-01-115)** on an ephemeral hosted runner with no secrets.
10. **A compromised Bayplan can do everything an agent's route table forwards, on every host whose agent is not read-only.** It can read the container, image, volume and network lists, the swarm's nodes, services and tasks, the events stream, any container's logs, and the **inspect of any single container, which includes that container's environment variables**. Bayplan masks those values for users without `secrets.reveal`, but the agent forwards the whole answer, so a secret passed to a container as an environment variable can be read through an agent. It can stop, kill and remove containers (and their anonymous volumes), and create and delete networks and volumes. It can **open a shell in any running container, as any user the image has, root included** (the agent refuses a privileged exec, but not a root user), and a shell in a container that is privileged, mounts the Docker socket or mounts the host's file system is root on the host. It can create a `local` volume that binds a host directory (T-04-10); it cannot mount it into a new container, because the agent forwards no container create, but a container someone else starts with that volume sees the host path. It cannot create or change containers, services or images, read a container's files, or read the swarm join tokens through an agent, and it can ask an agent to update or uninstall itself, with the limits above. Set `BAYPLAN_AGENT_READ_ONLY=true` on hosts Bayplan should only watch, avoid privileged and socket-mounting containers on managed hosts where you can, treat the Bayplan server as holding the inventory and the shells of every host, and prefer Docker secrets to environment variables for what you run.
11. **The standalone join token stays in `docker inspect` until it is rotated.** Once the agent has enrolled the token is not needed again; rotating it in Bayplan and recreating the container with the new command removes the exposure. A swarm keeps the token in a Docker secret instead.
12. **A broken agent image can leave one node's agent down.** A swarm rolls with Docker's own rolling update, whose default on failure is to pause: a bad image stops the first node's agent and leaves the rest on the old one until an operator runs `docker service rollback`. Bayplan shows the node as disconnected and, after fifteen minutes, the failed update. Releases are signed and pass the end-to-end run first (see the release checklist), which keeps the chance low, not zero.
13. **The agent's address changes only by pushing a new address to connected agents or by reinstalling.** The server accepts one audience, so an agent that dials a host or port that is no longer the configured one is refused, including one that was offline during the change. For 0.x this is decided (option B, 2026-10-04): Bayplan does not accept the previous address for a fallback period, because a second accepted audience widens what a handshake addressed elsewhere can be replayed against. The Settings confirmation and `docs/agent.md` say so.
14. **A leaked agent key is valid until its certificate lapses or an admin revokes the node.** Revoking is immediate, and an admin revoke also blocks the node from enrolling again, but there is no revocation list for a certificate that Bayplan itself has not seen used.
15. **Agents can be cloned.** A virtual machine copied from another shares its Docker engine ID, so Bayplan refuses it as a duplicate until the engine gets a new identity (see `docs/agent.md`). A node that is not refused for that reason, but shares an agent state volume with another, would share its key; keep the `bayplan-agent` volume per host.
16. **A flood of silent handshakes from four or more addresses can still fill the 64 slots (T-02-128).** One address, or one IPv6 /64, holds at most 16, so four are enough (4 x 16 = 64). Each slot is freed after 3 seconds, so the flood must open a new connection every 3 seconds per slot to keep it up. Connected agents are unaffected, and an agent that is refused waits and tries again.
17. **A loopback agent address admits plain connections from any peer (T-02-141).** When the agent address is on Bayplan's own machine, Bayplan accepts plain connections from any peer, because it judges the address agents dial and not the peer (a containerised Bayplan sees its local agent through the bridge gateway). An agent told to dial loopback sends nothing over a network, and a remote caller exposes only what it sends. Every agent still has to authenticate.
18. **The count of repeated refusals is lost on a hard kill.** The first refusal of each kind is always written in full and at once. The counter of repeats inside the open 60-second window lives in memory and is written when the window closes or at a clean shutdown, so a power loss or `kill -9` loses the count, not the refusal.
19. **File locks on network file systems.** `bayplan restore` and `bayplan key rotate` refuse to run while a server holds the data-directory lock, but a file lock is advisory and some network file systems (NFS, some FUSE mounts) do not honour it. Do not keep `/data` on one, or stop Bayplan yourself before running either command. Running either against a live server can corrupt the database.
20. **Administrators' usernames are shown to a user with no access.** The page for a signed-in user who can see no environment lists the usernames of the instance admins, so they know whom to ask. Any account, including a freshly invited one, can read them. Usernames are not secret in Bayplan, but they are a small disclosure.
21. **The scheduled backup's passphrase is readable by anyone who holds `/data` and the master key.** It must be stored to run unattended, sealed under the master key. Someone with a copy of the volume (which holds the key unless you supply it separately) can read it and open the backups made with it. Supply `BAYPLAN_ENCRYPTION_KEY` from a store apart from the volume, keep scheduled backups on a different volume, and use a passphrase that is used nowhere else.
22. **`unknown_agent` tells whoever holds an agent's key and certificate that the agent is unknown.** After a restore, an agent enrolled after the backup is refused with that reason, and the reason names a state of the database. Bayplan says it only after the signature checks out against the certificate's own key, so a copied or forged certificate learns nothing, and the answer is the same for every such agent. But it is more than the generic refusal a stranger gets.
23. **A leaked invite or reset link can be used by anyone until it is used, replaced or expires.** It is a bearer token, 72 hours by default. Bayplan sends no email, so the admin must pass it on privately, and a link pasted into a chat or a ticket stays readable there. Shorten `BAYPLAN_INVITE_TTL`, and regenerate a link you doubt.
24. **A backup file and its passphrase together are the whole instance.** A backup holds password hashes, the environments' certificate authorities and the full audit log. Anyone who can open it can sign in as any user after restoring it somewhere, and can issue certificates that the environments' agents accept. A weak or reused passphrase makes the argon2id cost irrelevant. Store the file and the passphrase apart, and treat both like the data volume.
25. **A process started in a browser shell can keep running after the shell is closed (T-04-80, accepted; D-30).** Closing the tab, losing the connection or an idle or administrator end closes the terminal, and Docker does not end a process that ignores the hang-up, so a daemon or a program started with `nohup` stays in the container. Bayplan does not search for or kill what is left, and the `shell.closed` row records that the process was still running. This is described under the audit of shells above; `docs/containers.md` says how to check (`docker top`, `docker exec <container> ps`) and stop it.
26. **Everyone who can read a container's logs sees whatever the application prints (T-04-63, accepted; D-23).** Logs are shown exactly as written and are never masked, and a Viewer can read them. An application that logs a password, a token or personal data shows it to every Viewer on that environment, and a downloaded log leaves Bayplan as a file. Only the opening and the download are audited, never the lines. Fix it in the application, or keep people who should not see it off that environment. `docs/containers.md` says so.
27. **Labels, and the driver options of networks, are shown as Docker reports them (T-04-41, T-04-30, accepted).** The container page and its Inspect JSON show every label to anyone who can read the container, the network and volume pages show their labels, the network's Inspect JSON carries its driver options, and the container search matches label values on the server, so a label value can be found by searching for it. The values of environment variables, log-driver options and volume options are masked (see "Values that can hold credentials" above), but a label is not. Do not put a secret in a label or a network option.
28. **An environment Admin can create a volume that binds a host directory, and a container that someone else starts can then see that directory (T-04-10, T-04-56, accepted).** This is described in residual risk 10. Bayplan cannot create the container that mounts it, and the volume's options, including the path, are in the audit log.
