# Bayplan threat model (Phases 1 to 9)

This describes what Bayplan protects against in its first four builds (install, sign-in and a read-only view of the local Docker host in Phase 1; remote hosts and swarms through agents in Phase 2; users, teams, roles, encrypted backups, restore and key rotation in Phase 3; changes to containers, networks and volumes, logs and shells in Phase 4; registries and image pulls in Phase 5; swarm services in Phase 6, compose stacks in Phase 7, stack history, adoption and drift in Phase 8, git-backed stacks in Phase 9), what it does not, and the risks that remain. Threat IDs (T-01-nn to T-09-nn) refer to the plans in which each mitigation was designed and tested.

This revision covers all nine phases. Phase 4 is described in "What Phase 4 adds": Bayplan's own Docker writes, the agent's route table and read-only flag, the browser shell, masking, stream limits, logs, the Events page, the proxy smoke test and the end-to-end proof. Its accepted risks are residual risks 10 and 25 to 29, and its boundaries are in the trust-boundary table.

Phase 6 is described in its own section, below the Phase 5 one: the agent's routes for services, nodes, secrets, configs, service and task logs and container stats, the host-policy check on a service spec and the opt-in that lifts it, how the server edits, creates and removes services, and restart-loop detection. It changes the headline below and residual risk 10, and adds residual risks 31 to 36.

Phase 7 is described in the last section before the residual risks: compose stacks, which let Bayplan read a compose file written by a person, deploy it to a swarm and to standalone hosts, and keep stack files and secrets. It adds the agent's container routes, the Compose engine on the server and its guard, and residual risks 37 to 44.

Phase 8 is described in "What Phase 8 adds", after the Phase 7 section: stack history and roll back to any revision, the discovery and adoption of stacks that Bayplan did not make (Portainer, `docker stack deploy`, `docker compose up`), and drift. It adds no agent route and no permission. It extends residual risk 41 (an adopted stack's draft holds environment values as literals) and adds residual risks 45 to 48.

Phase 9 is described in "What Phase 9 adds", after the Phase 8 section: stacks that follow a folder of a git repository, repositories and credentials, the webhook receiver, polling, auto-deploy and the mirrors on disk. It adds one unauthenticated route, a new way for the server to dial out, and residual risks 49 to 55.

## The headline

**Bayplan server compromise == root on every managed host.**

Bayplan manages Docker through the Docker API, and the Docker API is root-equivalent. A process that can talk to `/var/run/docker.sock` can start a privileged container that mounts the host's root file system, read any file, and change any setting. So whoever controls Bayplan controls every host it is connected to, whatever the individual buttons in its interface allow.

Three consequences follow, and the README repeats them before the install command (T-01-116):

- Mounting the socket is a decision about the host, not about an application. Do it only on hosts you intend Bayplan to manage. Nothing is managed until an admin opts in after setup, and the opt-in screen says the same.
- Every admin account is a root account on the managed hosts. Treat admin passwords, sessions and the machine that runs the browser accordingly.
- The strength of Bayplan's defences matters less than its exposure. Do not publish port 7480 to the internet. Put it behind TLS and, if you can, behind a network boundary or VPN.

Phase 2 adds remote hosts through agents, which widens the same statement to **every host with an agent**. Since Phase 4 an agent forwards changes as well as reads (see below): a Bayplan that is compromised can stop, kill and remove containers, open a shell in any running container, read container logs, and create and delete networks and volumes on every host whose agent is not read-only. A shell in a privileged container, or in one that mounts the Docker socket or the host's file system, is root on that host, so the headline holds through agents too. Since Phase 6 the agent on a swarm manager also forwards service creates, updates and removes, so a compromised Bayplan can create and change services without host access, and remove services, on every manager whose agent is not read-only. It cannot give a service host access unless that host's owner opted in with `BAYPLAN_AGENT_ALLOW_PRIVILEGED_SERVICES=true`: the agent refuses a spec that binds the Docker socket or a host path outside the data roots, adds a capability, lowers the sandbox or joins the host network. So by default it still cannot start the classic privileged container. **With the opt-in, a compromised Bayplan can run a privileged service on every node of the swarm, which is root on every node, so the opt-in puts the headline back in full.**

## Trust boundaries

| Boundary | What crosses it | Main controls |
|----------|-----------------|---------------|
| Browser to API | Sign-in, sessions, every change the UI makes | Server-side sessions, CSRF token, Origin check, strict CSP, per-route permission policy |
| Internet to setup and sign-in | The setup token, passwords | Setup token gate, rate limits, account lockout, one error for every sign-in failure |
| Bayplan to the Docker socket | Every Docker API call | Typed facade with a pinned method set (reads plus a closed set of container, network, volume and service changes and no passthrough), per-permission and audited write endpoints, `unix://` only, privilege drop to UID 1000. A standalone stack on this host is deployed by the Docker Compose engine, which creates containers, and it reaches the socket only through a guard that decides every method of the client and refuses all it does not need (see the Phase 7 section below) |
| The `/data` volume | The database, the master key, the setup token file, the TLS key | File modes 0600, ownership by UID 1000, key never logged, backups documented |
| Reverse proxy to Bayplan | Client addresses, scheme | Forwarded headers believed only from `BAYPLAN_TRUSTED_PROXIES` |
| Agent to Bayplan, `/agent/connect` | The join token (once), the agent's signed challenge, every Docker answer, update and uninstall messages | Verified TLS, per-environment CA and key-based authentication inside the tunnel, handshake limits, throttled audit of refusals |
| A stack author to the Bayplan server's files, network and programs | A compose file, its stack files and its variables | The file is parsed from memory with no directory: `include`, `extends`, `label_file`, `provider` and `use_api_socket` are refused, every `env_file`, `file:` secret and config must name a stack file (a database row), the server's own environment is never read, and the load has a 5-second deadline and a work budget |
| A stack made elsewhere to Bayplan's ownership decisions | The labels, names and objects of a swarm namespace or Compose project that Bayplan did not create, before and after it adopts them | Labels only find a candidate and never link it: a `bayplan.stack.id` label is a note and never a key, one function decides ownership, adopting writes nothing to the engine and is checked again on the server against a fingerprint, and Bayplan's own and agent stacks cannot be adopted |
| Bayplan to an agent's Docker socket | Docker requests Bayplan sends over the agent's tunnel | The agent's own route table (method, path, query keys and a rebuilt body for each call), its 64 KiB body cap (256 KiB for a service spec or a container create), its read-only flag and, for service writes and container creates, its host-policy check (a spec that gives tasks or a container host access is refused unless the host opted in), all enforced on the host |
| Signed-in users of different roles to the API | Every request for an environment or an administrative action | One permission registry, a role matrix generated from it, 404 for environments the caller has no access to, refusals audited and coalesced |
| An environment Admin to the people and teams of an instance | Giving, changing and removing access on one environment | Delegation capped to that environment and to Admin, Operator or Viewer; instance admins and all-environments access out of reach |
| The holder of an invite or reset link to Bayplan | A bearer token that sets a password | One-time, expiring, hashed at rest, in the URL fragment, never signs in, one answer for every dead link |
| A backup file outside Bayplan | Every user, hash, certificate authority and audit entry | A passphrase-derived key and an authenticated cipher, no master key inside, the passphrase never a flag |
| The offline command line on `/data` | `restore`, `key rotate`, `backup`, `user reset-password` | Runs as UID 1000, takes the data-directory lock, validates before it changes anything, audited as `system:cli` |
| The build pipeline | Source, dependencies, the two images (`bayplan` and `bayplan-agent`) | Pinned actions, licence gate, minimum release age, digest-pinned base, signatures and SBOM on both images |

## What Phase 1 builds in

**Docker access is narrow and typed (T-01-64, T-01-65, T-01-66; widened in Phase 4 by T-04-01 to T-04-05).** All Docker calls go through one package, `internal/dockerx`, and a lint rule keeps the Docker client out of every other package. The package exports typed methods only, none of which takes or returns a Docker library type, and a reflection test pins the exact method set. A pattern in the same test refuses names in the write and passthrough families (create, remove, start, stop, kill, exec, update, prune, raw, passthrough, plugins, swarm init/join/leave/unlock); each Phase 4 method that has to carry such a word is listed and reviewed by name. `DOCKER_HOST` accepts `unix://` paths only, and the environment never chooses the API version or TLS settings. Engines Bayplan does not support (older than Docker 24, rootless, Docker Desktop, Podman) are detected and refused with a reason rather than treated as supported (T-01-80). Since Phase 4 the facade also changes things, through a closed set of calls; that is described in "What Phase 4 adds".

**Default-deny authorisation (T-01-04, T-01-29, T-01-30, T-01-31, T-01-34).** Every route declares a requirement. Registering one without a requirement panics at startup, and a startup check walks the router to prove each route is guarded. The policy engine denies anything not explicitly granted, resolves the environment before the permission check, and writes an audit entry for every denial; if that write fails the request fails. Hiding a control in the UI is only convenience (T-01-58): the server decides.

**Sessions and CSRF (T-01-44, T-01-52, T-01-53, T-01-33, T-01-57).** Session IDs are 256 random bits and only their SHA-256 is stored. The cookie is `HttpOnly` and `SameSite=Lax`, and `Secure` with the `__Host-` prefix when the public URL is `https`. A new session is created at sign-in. Every state-changing request needs an `X-CSRF-Token` derived from the session with a key held in the vault, compared in constant time, and an `Origin` that matches the public URL. Only the cookie of the configured scheme is read: on an `https` instance the bare cookie is ignored, so one planted from a sibling host or over plain http cannot stand in for it (T-01-G07), and changing the public URL scheme signs browsers out once. Sessions end after 12 hours idle, remembered sessions after 30 days, and sign-out deletes the server-side row. Open event streams were authorised only when they opened, so they are re-checked on every 15-second heartbeat (session, user, environment and permission, without touching the session) and capped at one hour. Sign-out, a password change that ends other sessions, idle expiry, a disabled user, a removed or disabled environment or a withdrawn permission therefore ends a stream within a heartbeat, and the browser's reconnect gets a 401 (T-01-G08). The sign-in `next` parameter only follows same-origin paths.

**Sign-in hardening (T-01-50, T-01-51, T-01-42, T-01-43, T-01-45, T-01-60).** Passwords are argon2id (m=19456 KiB, t=2, p=1, per-hash salt), at least 12 characters, checked against an embedded common-password list and against the user name. Five failed sign-ins lock an account for 30 minutes, and there is a per-address limit. Unknown, disabled and wrong-password cases give one error and one status, and unknown users still pay the hashing cost. Hashing is limited to four at a time. Changing a password needs the current one, is throttled per user, ends other sessions and is audited.

**The setup token gate (T-01-36, T-01-38, T-01-39, T-01-40, T-01-41, T-01-46).** An unclaimed instance has a 128-bit token, compared in constant time, with a per-address limit, and every failure is audited with the address. Once an admin exists the setup endpoints answer 409. Completion re-checks the user count inside the write transaction, so two simultaneous attempts cannot both win. There is no development or configuration switch that skips the gate (T-01-09).

**Audit log (T-01-23, T-01-25, T-01-27, T-01-28, T-01-98, T-01-99).** Every entry is chained with an HMAC keyed from the master key, which is not stored in the database, so rows edited or deleted from the middle are detectable with `bayplan audit verify`. Appends happen in one immediate transaction, so concurrent writers cannot fork the chain, and a failed append fails the request instead of dropping the entry. Detail fields cannot carry secrets, and lengths are capped. Only admins can read the log, and exports leave out the chain internals. CSV exports neutralise formula-looking cells (T-01-97, T-01-103).

**Secrets at rest (T-01-15, T-01-24).** The master key is 32 random bytes, in `/data/bayplan.key` (mode 0600, written atomically) or in `BAYPLAN_ENCRYPTION_KEY` / `BAYPLAN_ENCRYPTION_KEY_FILE`. It is never logged, never in the database and never returned by an API; only derived subkeys are used. Settings are logged with secrets redacted.

**Running unprivileged (T-01-108, T-01-109, T-01-112).** The container starts as root only to fix the ownership of `/data` and join the socket's group, then becomes UID and GID 1000, in every subcommand, so the command-line tools never leave root-owned database files. The base image is distroless, with no shell. The self-signed TLS key is written 0600 under `/data/tls`.

**Browser hardening (T-01-03, T-01-05, T-01-06, T-01-113, T-01-114).** The Content-Security-Policy is `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; ...; frame-ancestors 'none'`, plus `nosniff` and `Referrer-Policy: no-referrer`. Fonts are bundled and nothing loads from another origin. The one concession is inline styles, which the toast library needs (T-01-63); scripts stay `'self'`. The end-to-end suite fails on any CSP violation and on any request to another origin. That check found, in Phase 4, that the form-validation library probed `eval` on every page before it had been told not to; every module now takes it from one place that turns the probe off first, so the policy needs no `unsafe-eval`. All strings from Docker, users or the audit log are rendered as text, never as HTML (T-01-48, T-01-59, T-01-81, T-01-84, T-01-91, T-01-101).

**Data safety (T-01-18, T-01-19, T-01-20, T-01-21, T-01-22, T-01-61, T-01-62).** Migrations are transactional and preceded by a snapshot with a free-space guard; a database from a newer schema refuses to start. A `/data` that is not a mount, or is tmpfs, is warned about, and the key-backup reminder is acknowledged in the audit log. All SQL is generated with bound parameters.

**Availability controls (T-01-17, T-01-54, T-01-71, T-01-79, T-01-87, T-01-90).** The HTTP server has header (10 s), read (30 s) and idle (120 s) timeouts, so a client that sends headers and withholds the body is cut off; the read timeout ends when a bodyless request is being served, so the events stream is not affected, and there is no write timeout. A locked-out sole admin has `bayplan user unlock`. Probes of a dead daemon back off, and a slow resource listing never holds up a probe, so a busy but healthy engine is not reported offline. The self-signed certificate is kept across container recreation, renewed before it expires, and never pinned with HSTS, so an upgrade cannot lock a browser out. Resource lists are capped and cached. Each principal gets at most eight event streams, and one daemon stream serves any number of viewers.

**Opt-in management (T-01-69, T-01-74).** The local host becomes an environment only through an explicit request by an admin, after the root-equivalence notice, and the change is audited.

**Supply chain (T-01-08, T-01-11, T-01-12, T-01-13, T-01-14, T-01-111).** Packages younger than 24 hours are refused by pnpm; the lockfile is committed and installs are frozen. A licence allowlist (Go on both architectures, and production npm packages) fails the build on anything else, and exceptions need a written reason. CI actions are pinned to full commit SHAs with read-only tokens and no secrets. Commits need a DCO sign-off. Release images use a digest-pinned base, keyless cosign signatures and an SPDX SBOM, and there is no `:latest` tag (T-01-76).

## What Phase 2 adds

**The agent connection is a new trust boundary, `/agent/connect`.** It is a WebSocket that anyone who can reach Bayplan can open, so it is hardened before any authentication: only `wss://` is accepted unless the development switch is set or the agent address is on Bayplan's own machine (loopback), which no other host can be told to dial, the `Origin` header must be absent (a browser sends one), at most 64 handshakes run at once and at most 16 of them from one client address (an IPv6 /64 counts as one address, and a forwarded address counts only when it comes from a trusted proxy), an agent that does not answer the challenge within 3 seconds is dropped, each address has an attempt budget, the warnings logged before admission are written at most once per address per minute (T-02-24), and a busy server answers `rate_limited` inside the protocol so a well-behaved agent waits. The refusals from a flood go through an audit throttle of their own (20 rows per address, then one per six seconds, then a counted summary), so a flood cannot starve the single database writer and still leaves a count. Only a peer in `BAYPLAN_TRUSTED_PROXIES` can make a connection count as `https` by sending `X-Forwarded-Proto`; the end-to-end run proves both sides: through a trusted proxy the agent connects, and without it Bayplan refuses with "did not arrive over TLS".

**Each environment has its own certificate authority, and agents authenticate with a key, not a shared secret.** The join token enrols a host once. The agent generates a key pair, proves possession of it by signing a challenge that is bound to the TLS session where the proxy allows it, and receives a certificate from its environment's CA, valid for 30 days and renewed over the live connection two thirds of the way through. After that the token is not used. Rotating or disabling the token never disconnects an enrolled agent, and revoking one agent never affects another. A compromised agent key gives access to that one environment's connection and nothing else; the CA key of an environment is stored sealed under the master key and opens only for its own environment. A hello whose certificate the environment's CA did not sign gets the same `auth_rejected` answer whatever its dates, so a forged certificate cannot tell whether an environment exists; only a certificate the CA issued is told it expired (T-02-21).

**On `wss://` the agent verifies Bayplan and never skips the check, and it does not dial plain `ws://` to another host unless `BAYPLAN_AGENT_ALLOW_INSECURE=true` is set on the agent (T-02-31 to T-02-34).** Only the install commands of a Bayplan that runs the development switch carry that setting, and only for a `ws://` address; stored addresses follow the same rule, and addresses Bayplan pushes are taken only as `wss://` over a verified session. Bayplan itself never hands out a plain agent address for another host without the switch: adding an environment, rotating a token, saving such an agent URL, the manual update command and the update hint all refuse it or leave it out (T-02-139, T-02-144, which replace the accepted T-02-137). Over `wss://` the agent trusts a certificate from the system's public CAs, or the pin of Bayplan's own self-signed key, or the pin of a certificate or certificate authority that the operator names with `BAYPLAN_AGENT_PIN` for a proxy with a private certificate. A pin only adds trust, a pinned authority counts only when the certificate presented chains to it for the address dialled, and there is no setting that turns verification off. Pins and new addresses that Bayplan pushes to an agent are accepted only on a session whose TLS was verified.

**The agent forwards a fixed table of calls, and the host owner can make it read only (T-04-06 to T-04-12, T-04-16).** Phase 2 gave the agent a table of reads; since Phase 4 it also holds a closed set of changes. The table, how bodies are rebuilt, what is refused whatever Bayplan asks, and the read-only flag are described in "What Phase 4 adds".

**Self-maintenance is the agent's only write, and it is narrow (T-02-88, T-02-90 to T-02-92).** Bayplan can ask an agent to update or uninstall itself. The agent accepts only an image from its own repository, only on a session whose TLS was verified (otherwise `insecure_session`), and only when the host owner has not set `BAYPLAN_AGENT_SELF_UPDATE=false`. A swarm update is Docker's rolling update of the agent's own service; a standalone update runs a short-lived helper container that recreates the agent with the same configuration and rolls back if the new container does not start. Automatic updates stay inside the compatibility window and a failed automatic update is not repeated for the same image. Every update and uninstall is audited under the admin or `system:agent-update`.

**Join tokens and CA keys at rest.** A join token is stored as a hash, never in the clear; a raw-byte search of the whole data directory after a real enrolment and rotation finds no join token, no secret part and no CA key (with a negative control that plants them). The token is shown once, in the install command, whose values are checked before they are quoted into a shell line or a YAML file (T-02-36) and which starts with a space so shells that skip space-prefixed lines keep it out of history. On a swarm it is held in a Docker secret. On a standalone host it is an environment variable of the agent container and so visible in `docker inspect` until the token is rotated.

**The session cookie is scoped to the base path (T-02-11).** Behind a subpath over `https` the cookie is `__Secure-bayplan_session` with `Path=/bayplan`, so another application on the same host does not receive it, and the end-to-end suite checks the name, path, `Secure`, `HttpOnly` and `SameSite` through a real proxy. The base path, host and origin come from the public URL only: `X-Forwarded-Host` and `X-Forwarded-Prefix` are never read.

**Proxy mistakes are noticed, not ignored (T-02-80 to T-02-82).** Bayplan records forwarded headers from an untrusted peer, requests whose host or scheme is not the public URL's, and agent upgrades that fail, and shows each as a bell item to admins who can read settings. It holds the sightings for an hour and at most 256.

**The end-to-end harness is built to be safe (T-02-100, T-02-101).** Its two privileged Docker-in-Docker containers and its throwaway admin are published on `127.0.0.1` only, with a seven-day certificate under `.devdata`. `docs/agent.md` labels `BAYPLAN_AGENT_ALLOW_INSECURE` as development only and never suggests turning verification off.

## What Phase 3 adds

**Roles are enforced by the server on every request, and the interface only follows (plan 03-05).** Access is the union of a user's own entries, their teams' entries and any all-environments entry, with no deny rules, evaluated on every request, so a removal takes effect on the next call and open streams for the environment are closed within a heartbeat. The role matrix is generated from the permission registry (`docs/permissions.md`), and an enforcement test drives every environment route as every kind of user (instance admin, Admin, Operator, Viewer, no access, disabled) and checks the answer against rules written independently of the code under test.

**An environment the caller cannot see is `404 environment_not_found`, like one that does not exist.** The visibility step runs before any environment lookup, so a user cannot tell a hidden environment from a missing one, and a disabled environment answers 409 only to people who have access to it. The refusal is still audited, with the reason that the environment was not visible. The one self-service route that takes an environment ID, recording a use (`PUT /api/me/recent-environments/{envId}`), answers and audits the same way, through the same coalescer, so probing IDs through it leaves the same trace and cannot flood the log. Instance admins are the only role that holds global permissions; no environment role grants one.

**Delegation cannot launder privilege (D-11, D-12; plan 03-20).** Only instance admins create users and teams or change who is in a team, and the instance-admin flag cannot be given through a team. An environment Admin gives access on their own environment only. The route they use has no scope field to abuse, and a crafted request that names an instance admin, another environment or an all-environments entry answers `403 delegation_denied` and is audited. The last active instance admin cannot be demoted, disabled or deleted, and the server counts after the change inside the transaction.

**Refusals are audited without letting a client flood the audit log (D-20; plan 03-10).** The first refusal for each user, action, reason, target and environment is written in full and synchronously, so a failed write still fails the request. Identical repeats within 60 seconds cost a counter and are written as one summary row, and ten or more in a window raise a bell item for instance admins. A table of open windows is bounded, and a full table writes through rather than dropping.

**Invite and reset links are bearer tokens, and are handled as such (D-22; plans 03-11, 03-15).** They are 256 random bits, stored only as a hash, valid once and for 72 hours by default, and placed after a `#` so they are not sent to Bayplan or a proxy in the request. The page moves the token into memory and removes it from the address bar before it renders. Accepting a link never creates a session, so a leaked link does not sign anyone in: it only lets someone choose that account's password, which is why the dialog tells the admin to send it privately. Regenerating a link or issuing a reset replaces the earlier one, a reset ends the user's sessions, every refused link is audited as `auth.link_refused` (rate limited), and the page gives one answer for expired, used, replaced and unknown links.

**Deleted users leave a tombstone (D-22c).** The username is reserved for ever, so audit entries keep their meaning and nobody can take a former user's name. Disabling a user ends their sessions and keeps their access, so enabling restores them.

**Automations run as their owner, rechecked every time (D-14; plan 03-13).** A git sync or webhook runs as a system principal on behalf of the user who set it up, against that user's current permissions. If the owner is disabled, deleted or has lost access, the run is refused, the automation pauses visibly, and an entry is written. Ownership moves only to a user who holds enough access, checked live, and an automation is never created with more rights than its owner has.

**Compose files that reach the host need an Admin (D-13, AUTH-10; plan 03-06).** The checker reads the compose file with a work budget (a hostile file cannot make it spin), reports the offending key and line, and treats any value it cannot resolve as unsafe. It flags `privileged`, added capabilities, devices, shared host namespaces, the host network, disabled confinement, and bind mounts of the Docker socket, runtime sockets and host roots. It errs towards flagging. The stack screens that call it arrive in later phases; the policy hook is in place now.

**Backups are encrypted, self-contained and never carry the master key (D-28, D-29; plans 03-02, 03-16).** The file is encrypted with a key derived from the passphrase by argon2id under an authenticated cipher, and every stored secret is re-encrypted for the file, so the master key is not in it and the file restores onto an install with a different key. The format carries a version and its parameters. The passphrase must be at least 16 characters, and it is never a flag or in the audit log. Sessions, invite and reset links and pending join tokens are left out. A test fails if any table is not classified as included or excluded.

**Restore is validated, staged and reversible (D-30; plans 03-16, 03-25).** The file and passphrase are checked, and the backup is migrated and re-keyed on a private copy, before the data directory changes. A newer backup is refused. The current database is saved first as `prerestore-<time>.db` (newest three kept), the swap removes the live write-ahead log before the rename, and a restore from the web interface rolls back to the snapshot when the restored database cannot start. The interface asks for the instance name and takes only instance admins. The audit chain is re-keyed under the new master key with a signed `audit.reanchored` entry saying where it came from, and `bayplan audit verify` passes afterwards. The upload is size-limited (`BAYPLAN_BACKUP_MAX_UPLOAD`), and only one is held at a time.

**Offline commands take the data-directory lock (plans 03-16, 03-18).** `restore` and `key rotate` refuse while a server holds it, and the refusal creates nothing: no key file, no staging directory, no snapshot.

**Key rotation is crash-safe and does not print the key (D-33; plan 03-18).** The new key is written 0600 and never shown. The old key is kept as `bayplan.key.old` and vouches for a `key.rotated` entry, so the re-signed chain can still be checked. An interrupted rotation is finished or discarded at the next start, and a stray `bayplan.key.new` is never taken as the master key on its own. A start whose key is not the database's active key is refused, rather than splitting the data across two keys. With a key from `BAYPLAN_ENCRYPTION_KEY` the new key goes to a file for the operator to apply.

**Scheduled backups are bounded (D-32; plan 03-27).** The schedule writes into one configured folder, and retention deletes only files that match `bayplan-backup-YYYYMMDD-HHMM.bayplan` in it. A backup made by hand with `bayplan backup` and no `--out` goes to the same folder under a different name (`bayplan-manual-YYYYMMDD-HHMMSS.bayplan`, never given to a file that exists), so retention neither counts nor deletes it and it cannot replace a scheduled one; the Backup page does not list or serve it. A failed run raises a bell item for instance admins. The schedule's passphrase is stored sealed under the master key.

**Agents after a restore (D-31; plan 03-28).** The environments' certificate authorities come back with the backup, so agents enrolled before it reconnect. An agent enrolled after it presents a certificate the restored database has no record of and is refused as `unknown_agent`, not trusted. The list of refused agents is in memory only, bounded, and aged out after 24 hours, and showing an install command makes a fresh token.

**The end-to-end suite proves the story in a browser (T-03-120).** An invited user, given Viewer through a team, sees one environment read only; another environment is "Page not found"; a direct API call for a hidden action answers 403 and appears in the audit log; and a backup is downloaded and restored over the running instance. These run on every pull request.

## What Phase 4 adds

Phase 4 is the first phase in which Bayplan changes Docker, so most of this section is about what is allowed, who may ask, what is recorded and what is kept out of a browser. The paragraphs cover, in turn, Bayplan's own Docker access, the agent's route table and read-only flag, the browser shell, masking, stream limits, logs, the Events page, and the proxy smoke test.

**Bayplan's own Docker access also changes things, through a closed set of typed calls (T-04-01 to T-04-05, T-04-22 to T-04-28).** Phase 1 was read only. Since Phase 4 the facade also changes things, through the same closed set of calls an agent forwards (see below):

- **Containers:** start, stop, restart, kill, pause and unpause, from a fixed set of verbs, with a stop timeout and a signal; and remove, with force and the container's anonymous volumes as the only options.
- **Networks:** create (bridge, overlay, macvlan and ipvlan only, with no way to ask for an ingress, config-only or config-from network), connect a container with only an alias and fixed addresses, disconnect without force, and delete.
- **Volumes:** create, and delete without force.
- **Shell:** an exec with only a terminal, a user, a working directory and a command. It cannot be privileged or carry environment variables. The browser shell opens one for a holder of `containers.exec` (see the browser shell paragraphs below).

The facade has no method to create or change a container, import, tag, push, save, load or build an image, remove an image with force, or send a raw request, so the API cannot reach one through Bayplan's code. (Since Phase 6 it can change a service, by sending the service's spec back to a manager with a new replica count; see the Phase 6 section.) Since Phase 5 it can pull an image (only a reference, a tag or digest and a platform), remove one without force, and inspect an image, read its history and ask a registry whether a pull would be allowed. Every write endpoint checks a permission per environment before it calls Docker: `containers.control` and `containers.remove` (Operator), `networks.connect` (Operator), `networks.manage` and `volumes.create` (Admin), and `volumes.delete` (an extra; removing a container's anonymous volumes needs it too). A bulk request names at most 25 targets. Each target is audited, failures included, and a write is never retried after a dropped connection. A row written after a change (a container action, a network or volume change, an administrator ending a shell) uses a context that outlives the request, with its own 10-second deadline, so a browser closed while the change ran cannot leave it without a record; the end-to-end suite found the gap for container actions and the fix was extended to the rest (plan 04-29). Bayplan's own server and agent containers can be stopped, killed, restarted, paused or removed only one at a time, with the container's name typed and checked on the server, and a bulk request skips them for those actions. Connecting one of them to a network or disconnecting it follows the same rule, so an Operator cannot cut Bayplan or an agent off a network by accident (fixed after the Phase 4 code review): the decision is made from a fresh inspect, a call without the matching name is refused with `confirmation_required` and audited, an `initiated` row is written before the call (a failed write stops it) and a `completed` row after, and a call whose connection dropped is recorded as `connection_lost`. Network and volume deletes re-read what uses them just before the call and refuse one still in use. **The local host has no read-only switch:** unlike an agent, the socket Bayplan mounts is managed through these endpoints by anyone holding the permissions above. Do not mount the socket on a host Bayplan should only watch; give that host an agent with `BAYPLAN_AGENT_READ_ONLY=true` instead.

**The agent's route table and the read-only flag are host-side defences (T-04-06 to T-04-12; the route tests, the independent fuzz oracle and the `FuzzBody` target in `agent/internal/proxy`).** The agent runs a reverse proxy in front of the Docker socket and checks every request against one fixed, ordered table of method, anchored path, allowed query keys with a pattern for each value, body kind and whether an upgrade is allowed. The agent decides from the bytes it receives, so a compromised Bayplan cannot widen the table. A request that is not in it gets a typed `agent_policy_denied` refusal, which the host's audit trail and Bayplan's audit log both record. The full list is in `docs/agent.md` ("What the agent forwards"). In short:

- **Reads:** ping, version, info, events, the four resource lists, the swarm lists, the inspect of one container, network or volume, the state of one exec, a container's logs (only the documented log keys), and volume disk usage.
- **Changes:** start, stop, restart, kill, pause, unpause and remove of a container (only the timeout, signal, `force` and `v` keys); create, start and resize of an exec; create, connect, disconnect and delete of a network; create and delete of a volume.
- **Images (Phase 5):** pull (`POST /images/create` with only `fromImage`, `tag` and `platform` and no body) and remove (only `noprune`, never `force`, so Docker itself refuses an image a container uses); inspect, history and the distribution check, none with a query. The registry credential header `X-Registry-Auth` is accepted only on pull and on the distribution check, as one base64url value of at most 16 KiB, and is deleted from every other request; `X-Registry-Config` is deleted from every request. The agent never decodes, logs or stores the header, and its refusals are reported without the query (T-05-07 to T-05-12). Image import (`fromSrc`, `repo`, `message`, `changes`), tag, push, save, load, build and prune stay refused.
- **Bodies are rebuilt, not passed through.** Exec create and start, network create, connect and disconnect, and volume create are decoded strictly into Docker's own request types, compared with a value built only from the allowed fields, and forwarded as that fresh value. A body larger than 64 KiB or a query larger than 4 KiB is refused.
- **Refused whatever Bayplan asks:** a privileged exec, an exec with environment variables or detach keys, an exec without a terminal, and a detached exec start; any upgrade other than starting an exec (`attach` and the file `archive` are refused); ingress, config-only and config-from networks, drivers other than bridge, overlay, macvlan and ipvlan, and IPAM options; a forced disconnect; cluster volumes; `link` on a container remove and `force` on a volume delete; changing a container, or creating an image; creating a container that gives the container host access, unless the host opted in (see the Phase 7 section); creating or changing a service whose spec gives tasks host access, unless the host opted in (see the Phase 6 section); a followed stats stream, container export and files; and `GET /swarm`, whose answer carries the swarm join tokens.

The host owner can set `BAYPLAN_AGENT_READ_ONLY` to refuse every request that is not a `GET` or `HEAD` before the table is consulted, so no shell can be opened and nothing can be changed, whatever a later release adds to the table. Bayplan reads the flag from the live session and refuses a change to such a host itself, as `host_read_only`, before it sends anything (T-04-16). An agent older than the server refuses the newer calls with `agent_policy_denied` until it updates. What a compromised Bayplan can still do through an agent is in residual risk 10.

**A browser shell is opened in two steps, so another site, another person or another sign-in cannot attach to it (T-04-76, T-04-77, T-04-81).** A browser cannot put a CSRF header on a WebSocket, and the router checks the CSRF token and `Origin` only on changing methods, so a shell is not one request. The first is a `POST` that passes both checks and needs `containers.exec` on the environment: it makes the exec and a pending session, and nothing is attached yet. The second is the WebSocket upgrade, which also needs `containers.exec` and claims that session. A session is single use, is bound to the user and to the hash of the sign-in session that made it, and waits 30 seconds for its browser, after which it is ended. A request for a session that is unknown, already claimed, expired, on another environment or bound to another user or sign-in gets the same 404, and the session is checked before the upgrade, so a request that the origin check refuses does not use it up. The upgrade is accepted only from the request's own host or the instance's public origin, scheme included, read on every request so that a change of the public URL applies at once (`OriginPatterns`, with the library's default origin check kept on). The option that turns that check off is never used, and the repository's TLS gate, `scripts/insecure-tls-check.sh` (run by `make lint`), fails the build when any Go file outside the one reviewed agent file names the setting that disables verification, which is also the name of the origin check's off switch. A shell is carried in 32 KiB writes with a 30 second write timeout, a 64 KiB read limit, a ping every 20 seconds and a resize limited to 1 to 1000 columns and rows (T-04-79); the connection's own deadlines are cleared, because a shell lives for hours, and the idle limit, the user's access and the server's shutdown end it instead.

**A browser shell is audited when it opens and when it ends, including when Bayplan stops (T-04-78, T-04-82 to T-04-88, T-04-94 to T-04-97).** Only the start and the end of a shell are recorded, never what is typed or printed; tests check the audit log, the server's own log and the page for terminal contents. `shell.opened` is written before the browser can attach, with the container, node, session, command, user, working directory and client address. If that write fails, the session is ended, so no shell runs that the log does not know about. `shell.closed` records how long the shell lasted, the exit code or that the process was left running, and why it ended. A server that stops tells every open shell's browser `server_shutdown` and does not finish stopping until each shell's `shell.closed` row is written. The HTTP server runs its shutdown hooks without waiting for them, so the graceful shutdown waits for every end in flight before the database closes; without that, a restart could lose the end of an open shell (fixed in plan 04-22 after its shutdown test caught it). A shell also ends, through the same audited path, when it has seen no input or output for the instance's idle limit (default 30 minutes, 5 to 240; the browser is warned a minute before and the limit is re-read on every check), with reason `idle`; and when its user no longer holds the shell permission, the grant on the environment or the sign-in, re-checked every 5 seconds, with reason `access_lost`. Some shells are refused before any exec is created, so they write no row: one on Bayplan's own server or agent container (decided from a fresh inspect, so Bayplan cannot cut itself off), on a read-only host, in a stopped container, through an agent too old to forward it, or beyond the per-user limit of open shells across environments (default 10). Only an instance admin can change the idle limit and the per-user cap, and each change is a `settings.updated` row. Every open shell is visible to whoever administers its environment: `shells.manage`, held by an environment Admin or an instance admin and never by an Operator or as an extra, lists each open shell on the environment with its owner's name, the container, the node, when it started and how long it has been idle (never what it shows or the command), and ends any of them. An administrator's end is two rows: `shell.ended`, with the administrator as actor and the owner, container, node and session named, and the owner's own `shell.closed` with reason `ended_by_admin`, so it cannot be done quietly. A person can list and end their own shells with the shell permission alone (`shell.closed`, reason `ended_by_user`); another person's session, another environment's session and one that has already closed all answer the same 404, even to an administrator on those routes. Both ends go through the same path as every other, so the shutdown wait above still holds. Bayplan remembers how each user last opened a shell in each image (the shell, a custom command, the user and the working directory) in `user_shell_prefs`, at most 200 rows per user, deleted with the user and carried in backups. It is meant to hold no secret, but a custom command is stored as typed, as it is in the `shell.opened` row, so do not put a password on a shell's command line. Closing a shell closes the terminal attach only: a process the user left running in the container keeps running (T-04-80, accepted), and its `shell.closed` row says so.

**Values that can hold credentials are masked on the server, and only `secrets.reveal` lifts the mask (T-04-40, T-04-111, T-04-59, T-04-70, T-04-55).** The container page, its raw Inspect JSON, the volume page and its raw Inspect JSON, and the notice for a log that Docker cannot read back all send values through one package. The values of a container's environment variables and of its log driver's options, its command line (the command, the entrypoint and, in the raw document, `Path`, `Args` and the command of its health check, whose mode stays visible), and the values of a volume's driver options (which, for an SMB or NFS volume created from Bayplan, can hold the share's password), are withheld unless the caller holds `secrets.reveal` on that environment: an Admin, an instance admin, or an Operator granted it. The names stay and the value, not even its length, is sent, and a raw document that cannot be read as a JSON object is an error and never passed through, so a malformed answer cannot carry a value past the mask. The audit row for a volume create records the options it was asked for with the value of any option, or segment of `o`, whose name contains `pass`, `secret`, `credential`, `token`, `key`, `auth`, `private`, `cert` or `identity` replaced, and the user and password part of any URL or share path removed, and cuts the text at 500 bytes after masking, so no row holds a share password. It is a list of names, not of allowed options, so a plugin volume driver whose secret option has another name is recorded (residual risk 29). What is not masked is in residual risks 26 and 27. Docker itself keeps a volume's options in clear on the host, so the mask protects the browser and the audit log, not someone who can run `docker volume inspect`; the create dialog says so.

**Streams are capped per person and per agent, and end when access ends (T-04-13, T-04-14, T-04-65, T-04-66, T-04-72, T-04-79, T-04-86, T-04-87).** A person may hold 8 live log streams (the ninth answers 429), two log downloads at once (429), and by default 10 shells across all environments (429 `shell_limit_reached`; an instance admin can set 1 to 50, and the cap is asked before anything is read from the engine and again under the registry's lock). A log stream lives at most an hour and is re-authorised every 15 seconds, and a shell is re-authorised every 5 seconds and closes after the idle limit, so a person who loses the permission, their grant or their sign-in loses the stream or shell within seconds. A download is copied through one fixed 32 KiB buffer a line at a time, so a log of any size costs the server no more than that, a single log line is cut at 256 KiB, and a page of earlier lines is limited to 8 MiB. Each agent session carries at most 64 server-opened streams, and at most 32 of those may be container log reads or shells; the other 32 stay for reads, actions and the events feed, so a crowd of log viewers cannot starve the dashboard or other people's actions. A request over the budget is refused at once with 503 `stream_busy` and never queued. Which requests are streams is decided from the request line that the server itself wrote; every other answer keeps the 64 MiB cap. Once an exec start that the server wrote is answered with the upgrade (`HTTP/1.1 101`), the connection is a shell and nothing written to it is classified again, so a person cannot type something that reads like a request line to release the shell's slot or put the cap back on it (fixed after the Phase 4 code review). The agent's answer only confirms an exec start the server already sent; it cannot make any other request a stream. These per-agent caps apply to agent sessions; the local socket has no tunnel. The caps for event streams are in the Events paragraph below.

**Opening or downloading a log is audited, and the lines are never kept (T-04-63, T-04-64, T-04-73).** `logs.viewed` is written once for each viewer window (the viewer's `sid`) with the container, node, how many lines and since when, so a browser that reconnects writes nothing more, and a new `sid` always writes a new row, which is more audit and not less; if the table that remembers the `sid`s is full, the row is written anyway. `logs.downloaded` is written when the response starts, with the container, node, the end of the range, the start if one was given and whether timestamps were asked for. Neither row holds a line of the log, and a test proves that a marker line written by a container reaches neither the audit log nor the server's own log. Unlike a shell's start, these rows are not a condition: if the write fails, the error is logged and the person still gets the log, and the viewer is not remembered as audited, so its next stream or page writes the row (fixed after the Phase 4 code review; before, a failed write could leave a viewer unaudited for an hour). A container whose log Docker cannot read back writes no row, because nothing was shown. The lines themselves are shown as the application wrote them and are never masked (residual risk 26).

**The Events page shows only an allowlist of each event's attributes, and keeps nothing (T-04-98 to T-04-104).** Docker puts every container label into an event's attributes, and for some events an environment value or a command line, so Bayplan passes on only twelve named keys: `name`, `image`, `exitCode`, `signal`, `type`, `container`, `driver`, `reason`, `destination`, `read/write`, and the two grouping labels `com.docker.compose.project` and `com.docker.stack.namespace`. No other label, environment value or free-form attribute reaches a browser, and a test pins the list. A container's `health_status` change, whose attributes can name the check command, is sent only as a refresh signal with no attributes and never appears in the feed, and the `exec_` events every health check and `docker exec` fire are dropped. What can still appear is an image reference (which can name a private registry), a mount's destination path, a container ID and a network's type and driver; on a swarm, service, node, secret and config events show their name and action only (T-04-101, accepted). The page and its feed need `environments.read` on the environment, which every Viewer holds, the same permission as the dashboard's feed; an environment the person cannot read answers as not found. Events are held in memory only: the server keeps the last 1000 per environment from at most the last 24 hours and loses them on restart, the tab keeps at most 1000, nothing is written to the database or the browser's storage, and viewing is not audited. The filters live in the URL, so a shared link carries the search text but no event data. Each stream is re-authorised every 15 seconds, lives at most an hour, and a user may hold eight event streams (a tab on the Events page holds two); a subscriber more than 64 events behind is dropped rather than buffered. Every value is rendered as text, never as markup, and links are built from route parameters, never from an attribute (T-04-102). Docker itself keeps only about its last 256 events and none across its own restart, so older history cannot be recovered.

**The proxy smoke test shows that each documented proxy carries the shell's upgrade and a log stream request to Bayplan, and no more (T-04-106).** `scripts/proxy-smoke.sh` runs the built image behind Caddy, nginx and Traefik, with the files in `docs/proxy`, at the root of a host and at `/bayplan`, and adds two checks for the correct setup (not for the deliberately broken nginx files). `shell_ws_reaches_bayplan` sends the upgrade request of a browser shell (`Connection: Upgrade`, `Upgrade: websocket`, a key and version, the session cookie and the public `Origin`) for an environment that does not exist, and passes only when the answer is a 404 whose JSON body is Bayplan's own `environment_not_found` problem. That shows the proxy forwarded the request, with its path under the base path, its cookie and its headers, to Bayplan, and did not answer 400, 426 or 502 itself. It does not show that a `101` upgrade completes or that terminal bytes flow. `log_stream_prompt` asks for a log stream of the same missing environment, with the session, and passes only when Bayplan's own JSON 404 comes back within 3 seconds. That shows the proxy does not hold a response to a stream request back. It does not stream a real log line, so it does not show that streamed lines are unbuffered; the script's existing check of the event stream's first frame does that for the one stream it opens. Neither check needs a container or a Docker socket. A real shell and real log lines through a proxy are covered by the end-to-end suite, in Chromium behind Caddy at `/bayplan` (see below); behind nginx and Traefik there are only these two request-level checks.

**The end-to-end suite proves Phase 4 in a real browser, through the proxy at a subpath, against a real engine (T-04-110).** It runs in Chromium against Bayplan behind Caddy at `/bayplan` over TLS, with a real Docker engine. Every test fails on any Content-Security-Policy violation or any request to another origin, and every address is under `/bayplan`. The Phase 4 tests, each passed in the full run (31 passed, none failed or skipped) and in three further runs of the Phase 4 project, plus one with HTTP/1.1 forced:

- A container started outside Bayplan appears in the list without a reload; it is stopped from its row through the confirmation dialog and started again, and two containers restarted together are both restarted in the engine, under one notice.
- The Logs tab streams stdout and stderr live with stderr marked, searches, downloads a file containing the lines, and pops out to a window that receives new lines at the same time as the tab; each page holds exactly one log stream.
- A shell opened from the Shell tab runs a command in the container: the file it creates exists in the engine and its output comes back over the WebSocket, whose upgrade was answered `101` at `wss://…/bayplan/…`, with the socket still open and no CSP violation. The policy's `connect-src 'self'` covers the `wss:` socket of the same origin, so the shell needs no wider policy (research question A4; observed in Chromium only).
- The Events page lists the container's `start` event.
- A network is created, joined with an alias, refused deletion while a container is attached, and deleted once empty; a volume is created and deleted only after its name is typed. Both are gone from the engine afterwards.

A tab on the Logs page holds three event streams and its pop-out one more, four in all, which stays within a browser's six connections per host even over HTTP/1.1 (research question A3); two Logs tabs over HTTP/1.1 would reach the limit (inferred, not measured). These tests do not check permission refusals, audit rows or masking, which the server's own tests cover. Not run: Firefox and WebKit, nginx and Traefik in the browser suite, a swarm environment and an older engine.

## What Phase 5 adds: registry calls from the server

Phase 5 lets the Bayplan server talk to container registries itself, to test a credential and to browse tags. That is a new way for a person who can add a credential to make the server open a connection to an address of their choosing, so the calls are fenced.

- **One egress policy for every registry call (T-05-38).** Each connection the server makes to a registry dials through a policy that checks the address after DNS has answered. Link-local addresses (`169.254.0.0/16` and `fe80::/10`, which hold the cloud metadata services), unspecified (`0.0.0.0/8`, `::`) and multicast addresses are always refused, so a name that resolves to one is refused too, and so are redirects and token endpoints. Private and loopback ranges are allowed by default, because self-hosted registries live there. An operator can refuse more with `BAYPLAN_REGISTRY_BLOCK_CIDRS` (comma-separated IPs or CIDRs, checked at startup; an invalid entry stops Bayplan and names it).
- **Redirects.** A redirect from HTTPS to HTTP is refused, and the probe of `/v2/` reports a redirect instead of following it.
- **Time and size.** Every call has a timeout (10 seconds to connect and to finish the TLS handshake, 30 seconds to the first byte, 30 seconds a call, 30 seconds for a whole test), and a manifest is read up to a fixed size.
- **A test is rate limited and audited (T-05-39).** At most 10 tests a minute per user, across both route families, and each is an audit row with the result of each step and never the secret. The answer to a test is a set of fixed codes; text from the registry is never returned or logged.
- **The credential's own CA (T-05-73).** A custom CA is at most 64 KiB and must hold a certificate. It joins the trust of that credential's calls only, never the server's own trust store, and changes nothing on a node.
- **The insecure switch (T-05-40, accepted, user-chosen).** A credential can carry an explicit switch that makes Bayplan's own calls to that registry skip certificate verification and fall back to plain HTTP when the server answers plain HTTP. It is off by default, per credential, and the sheet warns while it is on. It does not change any node: each node's Docker daemon needs its own `insecure-registries` or `certs.d` setup, and Bayplan never edits daemon settings. The plain HTTP fallback is built on the same egress policy (T-05-74), so the fenced ranges stay fenced with the switch on.

## What Phase 6 adds: swarm services and the host-policy check

Phase 6 lets Bayplan change swarm services. A service spec is a whole container specification, so a service write is a way to start containers on every node of a swarm. Plan 06-03 fences it before any plan lets the server send a full user-written spec (decision D-36).

**New agent routes.** On a manager the agent forwards the inspect of one service, the create of a service (`POST /services/create`), the update of a service (`POST /services/{id}/update`, with only the `version`, `registryAuthFrom` and `rollback` keys) and the remove of a service (`DELETE /services/{id}`, no query key). The create and update bodies are a service spec, capped at 256 KiB, decoded strictly into Docker's own type and forwarded as the re-encoded value; a task runtime other than container, a plugin spec and a network attachment spec are refused. The registry credential header `X-Registry-Auth` is accepted on the create and on the update, on the same terms as for an image pull. A read-only host refuses all three writes before any check runs. The agent also forwards the inspect of one node (`GET /nodes/{id}`, no query key, read-only and allowed on a read-only host). Its answer holds the swarm's TLS trust root and the node's certificate subject, which are public, and no join token. **The node update route (plan 06-15, T-06-42 to T-06-45).** On a manager the agent also forwards `POST /nodes/{id}/update` with only the `version` key. Its body is a node spec, capped at 64 KiB, decoded strictly into Docker's own type; the agent builds the value it forwards from the four fields an update may set (name, labels, role, availability), requires the role to be `manager` or `worker` and the availability `active`, `pause` or `drain`, and bounds the labels like every other label map. Any other field is a refusal. A read-only host refuses the route before any check runs. The route changes who may be a manager and where tasks may run, so on the server it needs `nodes.manage` (Admin) on the environment. The server judges a drain or a demote before it writes (`GET /api/env/{envId}/nodes/{nodeId}/impact` is the same judgement) and refuses with `confirmation_required` unless the node's name was typed when the change could cut Bayplan off, leave the swarm without a quorum or take the only connected manager agent (T-06-43); the check is on the server, not the page. It reads the node fresh and sends the version it was given, and a node changed in between is `node_changed` and is never retried (T-06-44). Every attempt on a node that exists is one audit row, `node.availability_changed` or `node.role_changed`, with the name, from, to, whether the name was typed, the warnings and the code (T-06-45). Bayplan warns and asks; the only blocks are Docker's own refusals, such as the demotion of the last manager. **Node labels (plan 06-16, T-06-46 to T-06-48).** The label save is the same node update route with only the labels changed, so it adds no agent route. Labels steer where services may run, so `PUT /api/env/{envId}/nodes/{nodeId}/labels` needs `nodes.manage` (Admin). The server refuses a label name that starts with `com.docker.`, `io.docker.` or `org.dockerproject.` (ASCII letters compared without regard to case) with `label_reserved`, although Docker itself accepts them, and refuses more than 64 labels, a name of 0 or over 256 bytes and a value over 4096 bytes with `label_invalid`, all counted in UTF-8 bytes and all before any read or write, so no limit is looser than the agent's (T-06-46, T-06-47). `POST .../labels/impact` writes nothing and judges the same labels against every service's placement constraints; it does not block a change that would unmatch a constraint, because the swarm only moves tasks and the page asks first. Every attempt on a node that exists is one audit row, `node.labels_changed`, with the name, how many labels were added, changed and removed, how many services are affected and the code (T-06-48). **Node remove (plan 06-17, T-06-49 to T-06-51).** On a manager the agent also forwards `DELETE /nodes/{id}` and **no query key at all**, so the `force` key that would remove a node that is still up can never be sent; Docker itself refuses a node that is not down, and a read-only host refuses the route before any check runs. On the server `DELETE /api/env/{envId}/nodes/{nodeId}` needs `nodes.manage` (Admin) and removes only a **worker whose state is down**: a manager is refused `node_is_manager` and a node that is not down `node_not_down`, both before anything is written, and the node's host name must be typed (`confirmation_required`), all on the server and not the page (T-06-49). The remove is sent once and never retried. Bayplan then revokes the agent whose swarm node is the removed one at once, with the reason `node_removed`, as the administrator and **without a block**, so a host that rejoins the swarm can enrol again with the join token (T-06-50); this is the reaper's revoke done at once, and a revoke that fails is logged and left to the reaper, which revokes the agent of a node missing from two node lists. A compromised Bayplan can therefore remove a node that is down and revoke its agent, but cannot remove a live one through an agent. Every attempt on a node that exists is one audit row, `node.removed`, with the host name, the agent revoked and the code, and the revoke is its own `agent.revoked` row with the administrator as actor (T-06-51). The stats route is covered below (plan 06-32).

**The host-policy check (T-06-07 to T-06-10).** Unless the host owner set `BAYPLAN_AGENT_ALLOW_PRIVILEGED_SERVICES=true` on the agent, the agent refuses a service spec that gives tasks host access, and says so with `agent_policy_denied: host_policy:`. Host access means:

- a bind mount of the Docker socket (or any container runtime socket), of `/`, or of any host path that is not under `/srv`, `/mnt` or `/media` (and not strictly below `/var/log`), or a Windows named pipe;
- a `local`-driver volume that binds a relative path or such a path (the engine passes a bind's device to the kernel unchanged and resolves a relative one against its own working directory, usually `/`), or that mounts any filesystem type other than `tmpfs` or a network share (NFS, SMB/CIFS, Ceph, GlusterFS), such as a host block device, an overlay of host directories or a host pseudo filesystem like `proc` (plan 06-50, T-06-145, T-06-146);
- a service mount whose volume names a driver other than `local`, or that mounts a cluster (CSI) volume (the agent only, because a plugin's options cannot be judged; the server and compose policies let an Operator use plugin drivers; plan 06-44, T-06-132);
- a service mount that names an existing volume whose backing on the manager's engine is one of the above (the agent only, because only the agent can ask the engine; plan 06-44, T-06-123);
- any added capability;
- SELinux disabled or the `spc_t` type, seccomp unconfined or custom, AppArmor disabled;
- a network attachment to the host network, whether it is named `host` or given by an ID that the agent looks up on its own engine and finds to be a network of the host driver (T-06-08).

The path rule is the same function the compose policy uses for stacks (`proto/hostpath`, T-06-09), so a path an Operator may bind in a stack is a path an Operator may bind in a service. A local volume's options are judged by a second function of that package, `LocalVolumeHostAccess`, which reads a device the way the engine does; the agent and the server's own policy both use it (plan 06-50, T-06-147). The compose policy, which has no caller before Phase 7, still reads a `driver_opts` device against the project directory. The same embedded vectors run against the agent's check and against the server's own policy. The opt-in is read once, at start, and only accepts `true` or `false` (T-06-10). The opt-in matters on every agent-managed host: a manager's agent judges service writes, including the volumes they name, and every agent, on a swarm node or a standalone host, judges volume creates. The server's own host is reached through the local socket and has no agent, so none of these checks runs there. The agent reports it in its policy facts, so Bayplan can tell before a write that a manager refuses host access, and a refusal reaches the person as `agent_host_policy`, with the setting that lifts it.

**Volume creates (plan 06-40, T-06-119 to T-06-122).** A service can mount an existing volume by name, so every agent, on a swarm node or a standalone host, applies the same rule to `POST /volumes/create`. Unless the host opted in, it refuses a `local` volume that the rule above refuses, and any driver other than `local`, with the same `host_policy` denial, which Bayplan shows as `agent_host_policy` (plan 06-42). Without this rule a compromised Bayplan could create a volume that binds `/` and mount it in a service. It changes the earlier behaviour of Create volume with a Host folder on an agent-managed host without the opt-in: a folder outside `/srv`, `/mnt` and `/media` is now refused there. Since plan 06-51 the fuzz invariants judge every forwarded volume with an oracle written apart from the rule (T-06-149), so a shape the rule misses fails the fuzz target instead of passing it.

**Named volumes in a service (plan 06-44, T-06-123, T-06-132 to T-06-134).** A manager's agent inspects each named volume a service create or update mounts, on its own engine, and refuses one whose driver is not `local` or whose options the same rule refuses. An anonymous volume, and a named volume the engine does not have, are created by Docker from the mount's own options, which the check above already judges. A lookup the engine does not answer refuses the write as an engine fault (`agent_engine_unreachable`), not as `host_policy`, so a transient fault is not shown as host access (plan 06-50, T-06-158). With the opt-in nothing is looked up. The fuzz invariants of plans 06-45 and 06-51 (T-06-135, T-06-149) hold both rules.

**The consequence the host owner should know.** Every service update carries the whole spec, so on a host without the opt-in Bayplan cannot change a service that already has host access: scale, force update and roll back included. Bayplan's own global agent service mounts the Docker socket; it is not scaled, and its updates run through the agent's own self-update path, not through this proxy.

**Masking extends to service specs.** Any page that shows a service's spec withholds the values of its environment variables, command, arguments, health check test and log-driver options from users without `secrets.reveal`, in the same way as for a container. The service page and its Inspect tab, the editor and its review, and a rotate's preview all show only the masked spec, with a withheld value written as `<hidden>` (D-39). The browser never holds the real value: a value you type over `<hidden>` replaces it, and one you leave alone is put back by the server when it builds the spec to send. The agent forwards the whole spec, so a secret passed as a service environment variable can be read through an agent by a compromised Bayplan (residual risk 10). Masking keeps values from people who can read a service, not from people who can change it; see residual risk 36.

**Editing, creating and removing services from the server (plans 06-01 to 06-27, T-06-63, T-06-64, T-06-78 to T-06-80).** None of these adds an agent route beyond the service ones above. Scale, force update, roll back and edit need `services.control` (Operator); create and remove need `services.manage` (Admin). Every one of them reads the service fresh, sends the version it read, and is sent once and never retried, so a service someone changed in between is `service_changed` and nothing is written. A create and an edit share one write path, so they cannot differ in image pinning, host-access policy, permission checks or cleanup. **The server judges the whole decoded spec**, not the fields the form shows: a caller below Admin is refused a spec with a bind mount outside `/srv`, `/mnt` and `/media` or of the Docker socket, a local volume that the rule above refuses, an added capability, a lowered sandbox or the host network (`privileged_service`), using the same path rule as stacks and the agent (`proto/hostpath`). The form authorises nothing: its bind-mount notice only words the rule, and the review step shows the server's decision (T-06-63). A rollback is judged too, on the previous spec it restores, before anything is sent, so a caller below Admin cannot bring back host access an Admin removed (`privileged_service`, plan 06-39, T-06-114). The editor applies exactly the spec its review judged and showed, and cannot be changed while the review is being checked (plan 06-41, T-06-124). A caller without `secrets.reveal` cannot add a secret the service does not use, on a review, an apply, a create, a rotate or a rollback that would bring one back: it is refused 403 `secret_reveal_required` before anything is written, and audited, while keeping, removing or re-targeting a secret the service uses stays Operator (plans 06-47 and 06-48, T-06-138, T-06-141). A secret is matched by the engine's secret ID, never by the name a spec gives a reference: a name alone is resolved through the swarm's secret list, and a reference whose name is not that of the secret its ID points at is refused 422 `spec_invalid`, whoever sends it, on a review, an apply, a create, a rotate's update, or a rollback to a previous spec that has one (plans 06-52 and 06-53, T-06-150 to T-06-152). A scale or a force update re-sends the service's stored spec with its secret references unchanged and adds none, so neither is judged. Because a spec can name a network, secret or config that does not exist, an apply creates them first (networks, then secrets, then configs, each needing the permission for that kind and audited with the source `service_apply`), writes their IDs into the spec, judges the policy again on the exact bytes it sends, and updates the service; **if anything after the first creation fails, every object this apply made is removed in reverse order** on a deadline that outlives the request, and the answer says which could not be removed. A staged secret's or config's value is held by the browser until the request is sent and is in no answer, log or audit row. The auto-rollback checkbox and every edit to an update setting seed Docker's defaults before they write, so ticking a box never silently turns a staged rollout into an all-at-once one (T-06-64). A stack's service cannot be edited or removed (`stack_owned`), and the service that runs Bayplan's own agent is removed only with its name typed, both on the server. Every attempt on a service that exists is one audit row (`service.updated`, `service.created`, `service.scaled`, `service.force_updated`, `service.rolled_back`, `service.removed`), failures included.

**Secrets (plan 06-22, T-06-65 to T-06-69).** On a manager the agent also forwards the list and the inspect of swarm secrets (`GET /secrets`, `GET /secrets/{id}`, neither with a query key), the create (`POST /secrets/create`, no query key) and the remove (`DELETE /secrets/{id}`, no query key). The create body is decoded strictly into Docker's secret spec and rebuilt from a name, labels and the value; a secrets driver (a plugin that runs privileged code), a templating setting, any other field, a name that is not a valid secret name, an empty value, a value of 512,000 bytes or more and a body over 1 MiB are refused. There is no secret update route: a secret is replaced by a new one. **Bayplan keeps no secret value.** The value is in the request body of a create and nowhere else: Docker does not return it, so Bayplan cannot show it even to an instance admin or a caller holding `secrets.reveal`, and the server never logs, audits, caches or stores it. An audit row for a create holds the name, the number of labels, the size in bytes and where the request came from; a refusal names a rule and never echoes what was sent. The server decodes the value from the request itself, checks its size (1 to 511,999 bytes) before anything is forwarded, and clears its copy of the bytes once the call has returned, though Go strings and the HTTP stack may hold copies until they are collected, and the browser holds the value only until the request is sent (residual risk 31). `secrets.read` (Viewer) lists secrets and the services that use them; `secrets.manage` (Admin) creates and deletes them, and a delete needs the secret's name typed and is refused while any service spec, including one scaled to 0, references the secret.

**Configs (plan 06-24, T-06-71, T-06-72).** On a manager the agent also forwards the list and the inspect of swarm configs (`GET /configs`, `GET /configs/{id}`, neither with a query key), the create (`POST /configs/create`, no query key) and the remove (`DELETE /configs/{id}`, no query key). The create body is decoded strictly into Docker's config spec and rebuilt from a name, labels, the content and, when asked for, the `golang` templating driver; any other templating driver, a driver option, any other field, a name that is not a valid config name, empty content, content of 1,024,000 bytes or more and a body over 2 MiB are refused. There is no config update route: a config is replaced by a new one. **A config is not encrypted and is not a secret.** Docker returns a config's content with every list and with every inspect, and Bayplan shows it: anyone with `configs.read` (Viewer) can read the content of every config of the environment on its detail route and in its inspect document, so passwords, keys and tokens belong in a secret. The configs list itself carries no content: the client drops it from every row as it arrives, so the content is in no cache and no list answer, and a swarm whose configs are too many or too large for one answer (the tunnel caps a response at 64 MiB) gets a 502 `config_list_too_large`. The server checks the size (1 to 1,023,999 bytes) before anything is forwarded. `configs.manage` (Admin) creates and deletes configs; a delete needs no typed name and is refused while any service spec, including one scaled to 0, references the config. The audit rows `config.created` and `config.removed` hold the name, the number of labels, the size, the templating and where the request came from, never the content.

**Rotating a secret or a config (plan 06-28, T-06-81 to T-06-84).** A new version of a secret or config is made by `POST /api/env/{envId}/secrets/{secretId}/rotate` and `.../configs/{configId}/rotate`, which add no agent route: they use the secret and config create, the service update and the remove that the agent already forwards. They create the new object with the old one's labels (a config also with the templating it was given), point every standalone service that uses the old object at the new one, one at a time in name order, and remove the old object when asked and when no service spec names it any more. A service a stack owns is skipped, because the stack's next deploy would put the old object back; the old object then stays. **A rotate needs two permissions** (T-06-81): `secrets.manage` or `configs.manage` (Admin) on the route and `services.control` (Operator) checked in the handler, whose refusal is audited as `permission.denied`; each service update runs the same steps as an edit, so the host-escalation policy judges the whole spec of every service for the caller and a caller below Admin is stopped at a service that has host access. The updates carry the version just read, are sent once and never retried, so a service somebody edited in between stops the run with `service_changed`. **The first failure stops the run** (T-06-83): the new object and the old one both stay, the services after the failed one are untouched, and the answer says which services moved. **The value is handled like a create value** (T-06-82): it is sent to the swarm once, cleared from the server's copy when the call returns, and is in no audit row, log, answer or cache; the page keeps it in state only and drops it when the dialog closes or the rotate succeeds. The preview lists each service's spec as it is and as it would be, masked for a caller without `secrets.reveal` by the same masking as the service spec page. **Audit** (T-06-84): `secret.rotated` or `config.rotated` (from, to, updated, skipped, removed_old, code) about the old object, `secret.created` or `config.created` with source `rotate` for the new one, `secret.removed` or `config.removed` with source `rotate` when the old one was removed, and one `service.updated` row for each service attempted.

**Service and task logs (plan 06-29, T-06-85 to T-06-88).** On a manager the agent also forwards `GET /services/{id}/logs` and `GET /tasks/{id}/logs`, with or without a `/vX.Y` prefix, and **only** the keys `stdout`, `stderr`, `timestamps`, `follow`, `details`, `since` and `tail` (the same value shapes as a container's logs). There is **no `until` key**: the engine ignores it on these routes, so the server cuts by time after it reads (T-06-88). A followed service log is as long-lived as a container's, so the tunnel classifies both routes as a log stream: uncapped, taking one of the agent's 32 interactive slots, so it is not cut at the 64 MiB response cap and a flood of them cannot starve the tunnel (T-06-85). The server opens **one** `ServiceLogs` follow on one manager (`Clusters.StreamOnManager`: the leader when connected, never retried on another manager, because a stream that dropped has already shown part of its answer) and the browser resumes with `after` or `Last-Event-ID` when it drops. The route `GET /api/env/{envId}/services/{serviceId}/logs/stream` needs `services.read` (Viewer) on the environment, allows at most 8 streams per user, lives at most one hour and re-checks the viewer's access on every heartbeat, as the container log stream does (T-06-85). The lines are application output, shown as written to anyone who may read the service, exactly as a container's log is (residual risk 26, T-06-86); **Bayplan stores, logs and audits none of them**: a test pushes a recognisable line through the stream and finds it in no audit row and no server log, and the only record is one `logs.viewed` row per viewer with target type `service`, holding the service name, the viewer's ID, the tail and the task and node filters that were asked for. The lines are merged in memory (the first answer sorted as a whole, live lines held for 500 ms), at most 32 MiB and 100,000 lines of the first answer at a time. Lines and task prefixes reach the browser as text and are drawn by the same ANSI renderer as container logs, which builds text spans and never markup (T-06-87).

**Earlier lines and downloads of a service's log (plan 06-31, T-06-91 to T-06-93).** `GET /api/env/{envId}/services/{serviceId}/logs` (a page of earlier lines) and `GET .../logs/download` (a file) both need `services.read` (Viewer) on the environment and add no agent route: they use the same `GET /services/{id}/logs` the stream does, once and to its end, without `follow`. The engine ignores `until` on a service log and applies `tail` to each task, so a page reads a window of time by `since` (10 minutes, widened eightfold up to 400 days, as a container's page does) and cuts at `until` in Bayplan, keeping the newest lines in a ring bounded by count (at most 2,000) and by size (8 MiB); a download reads the range and cuts it the same way. **A download holds each task's lines in memory up to 32 MiB in all** (T-06-91): past that, the oldest line of any task is dropped, the first line of the file says the oldest lines were left out, and the held lines are merged k ways and written through one 32 KiB buffer, each line starting with the task's name and its UTC time. **A user runs at most 2 downloads at once and the server 4**; the one past either is refused with 429 `stream_busy` before anything is read, and reading a range is bounded at 15 minutes. **Each download is audited** (T-06-92) as `logs.downloaded` with target type `service`, the service name and the effective range (`since` if given, `until`, which is now when none was asked for), written once the range has been read and before the file starts; a refused download and a page are not audited as downloads, and a page shares the audit memory of the stream, so a viewer is audited once as `logs.viewed` however it reads. No row holds a line of the log. As for a container's, a downloaded file leaves Bayplan as a file and its lines are shown as written (T-06-93, residual risk 26).

**Container stats (plan 06-32, T-06-94, T-06-95).** The agent forwards `GET /containers/{id}/stats`, with or without a `/vX.Y` prefix, with **only** the keys `stream` and `one-shot`, and `stream` may only be `0` or `false`: the agent answers one sample and never holds a stats stream open, so the route takes no interactive slot and is capped like any other answer. A sample holds counters (CPU time, memory, network and block I/O bytes) and no names, labels or environment. `GET /api/env/{envId}/containers/{containerId}/stats/stream` needs `containers.read` (Viewer) on the environment, allows at most 8 streams per user, lives at most one hour and re-checks the viewer's access on every heartbeat, as the log stream does. **The server samples on behalf of its viewers, so the fan-out is bounded** (T-06-94): a container has one sampler however many people watch it, a sampler exists only while at least one viewer does, it asks every 2 seconds, it never repeats a request for a container while the last is pending, and at most 8 requests are in flight on one node at once (each node counts on its own), so fifty watched containers on one node cannot take that node's tunnel. **Nothing is stored** (T-06-95): the hub keeps the previous raw sample of each watched container in memory to turn two readings into rates, sends each derived point to the viewers and forgets it; no sample reaches the database, the audit log or the server log (a failure to read is logged with the container and the error, never a value), a test streams samples and finds none of them in an audit row or in the log, and another fails the build if the stats files import a database, the audit writer or the file system. The history a user sees is the last 150 samples held by their own browser tab and dropped when the tab leaves the page. The stream is not audited: it carries counters, not application data. The limits shown with a container (memory and CPU) come from its inspect, never from the stats, whose memory limit is the host's RAM when the container has none.

**Service, list and node stats (plan 06-33, T-06-96, T-06-97).** Four more streams total what the container stream samples: `GET /api/env/{envId}/services/{serviceId}/stats/stream` (the sum over a service's running tasks, with each task's own sample), `.../services/stats/stream?ids=` (one total per service for the rows of the services list), `.../containers/stats/stream?ids=` (one sample per container for the rows of the containers list) and `.../nodes/stats/stream` (the sum of the running tasks on each node of the swarm against the node's CPUs and memory). They add no agent route: every sample is the one-shot container stats route above, asked through the same shared hub, so a container that two surfaces watch is sampled once and the per-node cap of 8 requests in flight holds for all of them together. The service, services-list and node streams need `services.read` (Viewer) and the containers-list stream `containers.read`, each on the environment, and re-check the viewer's access on every heartbeat. **The fan-out a browser can ask for is bounded** (T-06-96): a list stream takes at most 100 ids and answers more with `422 too_many_ids` before anything is sampled, the four streams share a limit of 8 open per user that is separate from the container Stats tabs', each lives at most one hour, and the page asks only for the rows that are on screen and in a group that is open. The node stream samples at most 1000 running tasks and says `partial` when it cut the list. **Nothing outside the environment can be sampled** (T-06-97): a service or task is found only through the environment's own manager, and a container id of the containers list names a node that the hub asks through the environment's aggregator, which refuses a node that is not a connected, unrevoked node of this environment; that container reads as having no data and no engine is called. A task on a node with no connected agent is never sampled and is reported as not reporting. As for the container stream, nothing a sample holds is stored, audited or logged.

**Restart-loop detection (plans 06-34 to 06-36).** It adds no agent route and no Docker write. For services the server reads the failed and rejected tasks the manager already returns; for containers it reads the die events the agent already forwards. The thresholds are two columns on the environment (2 to 50 failures, 1 to 120 minutes) changed by `environments.configure` (Admin), audited as `environment.restart_loop_settings_changed`. A mute is one row keyed by environment, kind and target, written in one transaction with its audit row (`restart_loop.muted`, `restart_loop.unmuted`), needs `services.control` or `containers.control`, and silences only the bell and the badge, never the failure itself. Health-bell and dashboard entries are shown only to people who can read the services or containers concerned. A flag carries the latest task error as Docker wrote it, cleaned for display, which any Viewer of the service can already read on its Tasks tab.

## What Phase 7 adds: compose stacks

Phase 7 lets a person write a compose file and have Bayplan deploy it. A compose file is a program for a Docker host: it chooses images, commands, mounts and networks, so deploying one is a way to start containers. A compose file is also text that a person with `stacks.update` (an Operator) wrote and that Bayplan parses on its own machine, so reading it is a boundary of its own. This section covers both, and then the three routes the agent gained so that the Compose engine can run through it.

**Server-file reads through compose (plans 07-06, 07-12, T-07-26, T-07-27, T-07-28).** Compose can read files: `env_file`, a secret or config `file:`, `include`, `extends` and `label_file` all name one, and a relative path or a symlink can lead out of the project directory. **A stack has no directory.** Its files are rows in the database, each stored under a path that the one path rule accepts (relative, plain names, no `..`, no backslash, no colon, no control or format character, at most 255 characters in all and 100 in a name, at most 50 files, 1 MiB each and 8 MiB in all, so there is nothing for `..` to climb out of). The load reads the compose file from memory, takes its variables from the stack's table only and runs in a working directory that exists on no host. Before it, a prescan of the raw YAML (which opens no file) refuses `include`, `extends` and `label_file`, requires every `env_file` entry and every top-level `file:` to name a stack file by a valid path (an illegal path is `path_illegal`, a missing file `file_missing`), and measures the file with every alias followed, so a file built to expand into millions of nodes is `compose_too_complex`. After the load an assertion reads the project again and refuses a path that is not a stack file. **The symlink class is unreachable**: a stack file is a row, not a file, so there is no link to follow, and no code path reads `/data`, `/etc` or any other file of the server on behalf of a stack (the loader is never given a file system; a test sets an environment variable of the process and shows it never reaches interpolation, T-07-48). A hostile corpus and fuzz targets hold the prescan (including `FuzzCheckResolved` for the host-access rules). The check that runs as a person types is bounded (5 seconds, at most 2 at once per person, a compose file of at most 1 MiB), needs `stacks.read` and answers with messages built from the stored bytes and positions only. `env_file` is read once, by Bayplan, from the stack's own files with Compose's parser (T-07-57), so the two targets can never see different values.

**Remote include and other fetches (T-07-27, T-07-97).** A remote `include` would make the server fetch a URL, and a `provider` service would make the Compose engine run the program its type names on the server (`exec.LookPath`). Both are refused in the prescan and in the preparation of a standalone project, for every role, as are `models`, the lifecycle hooks (`pre_start`, `post_start`, `pre_stop`) and `use_api_socket` (the engine turns it into a bind mount of the host's Docker socket that the host-access rules never see). `build` is stripped after the lint has judged it, and a service with a build and no image is an error, so no build context is ever sent to an engine (T-07-36). Bayplan never calls the engine's own project loader: it prepares the project itself and sets the labels that loader would have set, with neutral values (`/bayplan-stack` and `compose.yaml`), so no path of the server reaches a host.

**Host escalation through variables, and the re-check (T-07-66, T-07-70, T-07-86).** A compose file that gives containers host access needs Admin (decision D-13). The rules run on the **rendered** stack, with every variable filled in, so `${DATA}:/data` with `DATA=/` is judged as a bind of `/`, and the converted swarm service is judged as well (the same functions as the service editor, in `proto/hostpath` and `internal/rbac/swarmspec`). **They run again at the deploy, for the person who deploys, and once more inside the job under the operation lock**, before the first write, so a draft that changed between the review and the deploy, or a role that changed meanwhile, is judged on what is deployed, not on what was reviewed. The deploy also takes the draft's version and the image pins from the review and refuses a pin the server would not have chosen (`pins_invalid`) or a draft that moved (`draft_changed`). A roll back is judged on the version it restores, for the caller (T-07-91), so someone below Admin cannot bring back host access an Admin removed. Two gaps remain and are open decisions: `sysctls` and `ulimits` are not in the rule set (residual risk 40), and behind an agent a `service:X` namespace or `volumes_from` is refused as host access though the manager does not judge it so.

**Secrets in reviews, diffs, the console, logs and the audit log (T-07-46, T-07-62, T-07-69, T-07-76, T-07-81, T-07-141).** A secret variable is sealed under the master key; a secret file (a file a `secrets:` entry names) is sealed with a row-bound context, so one stack's ciphertext does not open as another's. **Both read as `<hidden>` in every answer**: the draft, the check, the review and its field diff (equality is decided before masking, and a change is shown only as a path), the rendered YAML, the concurrent-deploy views, the Resources tab (which reads names, labels and versions, never a value, because Docker returns none) and the browser's query cache. The masker is built from the stack's secret variables and secret files, those of the version that last ran and those of the draft, and removes their values from the review, from the deploy's job items and output (before the hub stores them, with control characters removed and 2,048 characters kept), from every streamed and downloaded stack log line and from errors. A log that cannot be masked is not served (503). **Reading a value is one audited act**: it needs `secrets.reveal`, the `stack.value_revealed` row (stack, kind and name, never the value) is written first and a failure to write it means no value is sent, the answer is `no-store` and the page keeps the value for 60 seconds. The audit log of every stack action holds names, counts and results and no value. What masking does not do is residual risk 41.

**The Compose engine and its guard (plans 07-20 and 07-21, T-07-96 to T-07-104).** A standalone stack is deployed by the Docker Compose engine (SDK v5.6), which is Docker's own code for `compose up`, so that dependency conditions, recreates and orphan removal behave as `docker compose` does and carry its labels. It runs **inside the Bayplan server**, over Bayplan's own Docker client, and only `internal/dockerx` may import it (a lint rule, `compose-sdk-seam`, fails any other import). The client it holds is wrapped in a **guard that decides every method of the engine client**: the methods the engine needs are allowed with their arguments checked, and the other 68 are refused, in a list closed against the whole interface, so a method a later version of the client adds is refused until someone decides it. The engine's configuration directory is private, empty and 0700 under the data directory, holds no registry credential, and its prompts are always answered yes and its output discarded; it is limited to 8 concurrent operations. **Bayplan pulls images itself with the stored credential** (`Resolver.AuthFor`, sent in the pull request alone and never in a job item, an output line or a log), and only for a service whose container the deploy creates or recreates, so the engine's own anonymous pull is not needed (residual risk 42 for `pull_policy`). Behind an agent the engine's requests go through the tunnel to the agent's route table, which is the second gate; the 29 requests a real engine sends for a full deploy, stop, start and removal are recorded and replayed against the allowlist, and no rule was widened to make it pass.

**Failure, cancel and interruption (T-07-87 to T-07-90, T-07-103).** A failed or cancelled deploy removes only what it created and nothing uses, judged by the stack's ID label and by the state of the host read again, without force and without volumes; a volume, a running container or an object of another stack is never touched. A deploy that was running when Bayplan stopped is marked interrupted at the next start, and nothing retries or rolls back by itself. One stack operation runs per environment (409 `operation_locked`), at most 5 jobs run per person, and the console, the job's stream and the job list check `stacks.read` on the job's own environment and that the job belongs to the stack, so a job of an environment the caller cannot read is a 404 (T-07-83, T-07-92).

**Foreign stacks (T-07-68).** A stack whose name matches a swarm namespace or a Compose project that Bayplan does not manage is refused at the create, the review and the deploy, with the labels read through the engine's own filter type, so a deploy never takes over a stack, and an object another stack owns is never removed. A `bayplan.stack.id` label is trusted only when the stack of that ID has the name the object shows (T-07-146). Since Phase 8 the one way to take a foreign stack over is adopting it, an explicit act of an environment Admin that changes nothing on the engine ("What Phase 8 adds").

**The container create route (plan 07-02, T-07-06 to T-07-09).**
**The container create route (plan 07-02, T-07-06 to T-07-09).** A standalone stack is deployed by the Compose SDK, which creates containers, so every agent forwards `POST /containers/create` with only the `name` and `platform` query keys (shape-checked) and a container spec capped at 256 KiB. The body is decoded strictly into Docker's own type and rebuilt from an allowlist of the `Config`, `HostConfig` and `NetworkingConfig` fields the SDK fills; any other field set is a refusal, and a read-only host refuses the route before the body is read (T-07-08, T-07-09). Unless the host owner set `BAYPLAN_AGENT_ALLOW_PRIVILEGED_SERVICES=true`, the agent refuses a create that gives the container host access: privileged mode, added capabilities, devices, host or foreign-container namespaces, a cgroup parent, volumes from another container, emptied masked paths, a runtime other than `runc`, a lowered seccomp, AppArmor or SELinux sandbox, a bind of a path outside the data roots or of a runtime socket, a volume plugin, and a named volume found on the agent's own engine to bind the host (T-07-06, T-07-07). The path and volume rules are the functions the service check and the compose policy use (`proto/hostpath`); the cases are the shared container vectors, and a second, independent rule judges every body the fuzz target forwards. With the opt-in, a compromised Bayplan can start a privileged container on that host, which is root on that host, as it can start a privileged service on a swarm.

**The container archive, rename and image inspect routes (plan 07-04, T-07-16 to T-07-19).** The same SDK injects a stack file secret or config into a container just before it starts, with a tar written through `PUT /containers/{id}/archive`, renames a container it recreates, and inspects images with the `manifests` and `platform` keys. The agent forwards the rename (only `name`, no body) and the two inspect keys, and the archive write only as a tar of exactly one regular file with a clean name, a mode with no setuid, setgid or sticky bit, no link target, device or extended record, at most 1,000 KB of content and nothing but zero padding after the end of the archive, at `path=/` and with `copyUIDGID` false, into a container that carries the `com.docker.compose.project` label and is not running (T-07-16, T-07-17). The agent asks its own engine for the container, and an engine that does not answer is a 502, never an allow (T-07-19). The body is capped before it is read (T-07-18), a read-only host refuses all three before any body, and the tar parser is driven by a fuzz target that checks every accepted archive against an independent reading. A compromised Bayplan can therefore write one ordinary file of its choice into a compose container on a managed host, which is what a stack's own secret or config does anyway; it cannot write a link, a device, a setuid file or a second file, or write into a container Compose did not create. The not-running rule keeps the route from being a general way to write into live containers; it is not a boundary against a compromised Bayplan, which can stop a compose container and then write to it. The container is checked once, so one started between the check and the write is not caught (residual risk, same effect).

## What Phase 8 adds: history, adoption and drift

Phase 8 lets Bayplan roll a stack back to an earlier revision, list and adopt stacks it did not create, and notice that what runs no longer matches what was deployed. Adopting is the first time Bayplan takes responsibility for objects it did not make, so most of this section is about who owns what and what is shown to whom. It adds no agent route (every read and write it needs was already in the table) and no permission: adoption uses `stacks.create` (an environment Admin), a roll back and a restore use `stacks.deploy`, accepting live state uses `stacks.update`, and the rest is `stacks.read`.

**Roll back to any good revision judges the revision, not the person's intent (T-08-09 to T-08-14, T-08-18 to T-08-20, T-08-80 to T-08-82).** A roll back restores a stored revision exactly, with its stored image digests and **no registry or tag lookup** (T-08-12, T-08-18), so a tag that moved cannot change what comes back; tests assert that no distribution request is made, on a swarm and, against a real engine, on a standalone host. Only a revision whose deploy finished well can be chosen (`revision_not_good`, T-08-10), and the revision is read by (stack, number) after the stack is read by (environment, ID), so another environment's revision is a 404 (T-08-06, T-08-13). The host-access policy is judged on the **restored** copy for the person who asks, in the review, in the route and again in the job under the lock (T-08-09, T-08-19, T-08-80), so someone below Admin cannot bring back host access an Admin removed. The deployed revision is checked again under the operation lock (`deployed_changed`, T-08-11, T-08-81), and the foreign-project check runs before any write (T-08-20). A roll back and a restore are audited as `stack.deployed` with mode, revision and the revision restored (T-08-14, T-08-82). Revisions are append-only: a roll back adds one.

**Revisions are pruned, and pruning takes sealed values with it (T-08-21 to T-08-25).** Bayplan keeps the newest N revisions of a stack (20 by default, 5 to 200, an instance setting). One SQL statement deletes the rest, **never the newest good revision and never one that is still deploying** (T-08-23), and the foreign keys take each deleted revision's files and variables with it, so a sealed secret variable or secret file does not outlive its revision (T-08-21). Lowering the limit deletes in the same transaction that stores it and the audit row (`settings.updated` with the old limit, the new one and the count, T-08-25), needs `settings.write` and is confirmed in the page. Residual risk 45 covers what a delete does not wipe.

**Discovery reads labels and trusts none of them (T-08-28 to T-08-35, T-08-47, T-08-60, T-08-67 to T-08-69).** A swarm stack is the services that share a namespace label, a standalone stack the containers that share a Compose project label. Nothing is stored, no extra engine read is made (the list's cached data is grouped), and the name is used as a label filter value through the engine client's own filter type and compared exactly, so a name cannot add a filter or reach a path (T-08-33, T-08-36, T-08-37; the stack-name rule has no dot, slash, space or percent). **A `bayplan.stack.id` label is never a key.** A stack made by another instance, or by this one before a restore, shows as unmanaged with a note and the ID only sets a flag (T-08-28); for an adopted stack the ID it carried is recorded as `PriorID` and widens ownership of that namespace's workloads only until the first good deploy, and never links another stack (T-08-47). After the first good deploy a new service in the namespace with no ID is a foreign service, and the deploy stops at a name clash instead of taking it over (T-08-60); Remove keeps only what the ownership function owns, so a late foreign service, an external network, secret or config is never removed (T-08-62, T-08-67). **One function decides ownership** (`Ownership` in `internal/stackops`), and a test parses the stack code and fails on any other place that decides it by an ID label (T-08-69). Bayplan's own stack and a stack that runs an agent are listed and flagged, and adoption is refused for them on the server and disabled in the page, so Bayplan cannot be made to deploy over or remove itself (T-08-49).

**Adopting is a recording, checked twice (T-08-46, T-08-48, T-08-51, T-08-54, T-08-57).** The adopt check reads what runs and builds the definition on the server; **the browser sends a fingerprint of what it checked, never a definition**. At the commit the server reads again, rebuilds itself, compares the fingerprints (409 `adopt_stale`) and stores the stack, its draft and revision #1 in one transaction under the environment's operation lock (T-08-46). A pasted original file is never trusted from the page either: it is checked again at the commit by the same check as any draft and stored as written (T-08-57). **Nothing is sent to the engine by adopting** (tests assert the engine received no write and, on a real swarm and a real standalone host, that service versions, network, secret and config IDs, container states and a volume's creation time are unchanged). The adopt check is `stacks.read` and the adopt is `stacks.create`, an environment Admin (T-08-48); **a pasted file is checked only by a caller who also holds `secrets.reveal` (403 `secret_reveal_required` otherwise, T-08-52)**, because the check compares the file with the running values and its answer (clean, matches, the number of gaps, the path of a hidden change) would tell a caller without reveal whether a guessed value is the running one; the host-access policy is not judged at adoption, which only records what already runs, but the check lists every host-access setting and every later deploy runs the policy for its caller (T-08-54). The adoption is audited as `stack.adopted` (T-08-51).

**A pasted compose file is read by the one checker (T-08-56, T-08-58, T-08-59).** The file is up to 1 MiB and goes through `stacks.Check`, the same load that reads every draft: no `include`, `extends`, `label_file` or `provider`, every `env_file` and `file:` must name a stack file, and nothing is read from the server's file system. A test fails if any other loader is used for it. In the browser the pasted text and the variable values are plain component state, with no storage, URL, toast or cached query, cleared on cancel, on leaving the page and on success. A variable the person marks secret is sealed like any secret variable.

**What a reader without `secrets.reveal` is not shown (T-08-15, T-08-32, T-08-39, T-08-44, T-08-52, T-08-70, T-08-73, D-47).** Every view of **live** state that Phase 8 adds is masked for a caller who may not reveal: the generated compose preview of an unmanaged stack, the adopt check and its differences (the rebuild check; a pasted-file check needs `secrets.reveal` itself, so it cannot be used to guess a value), a revision's Changes tab, and the drift page, for a swarm and for a standalone host. The environment values, command, entrypoint, health check command and log options of the services are withheld (the path that changed is still listed, so a change is not hidden, only its value), the decision is the same `CanReveal` rule as the inspect views, and the unmanaged read routes hold no such field at all (a test scans the body). The preview reads secret and config **names** only, never their data, and never inspects them (T-08-40). Turning the redaction off was shown to fail the drift route's test.

**The stored definition of an adopted stack is not masked this way.** Environment values are copied into it as literals (D-15), and Bayplan does not guess which are secret. That is residual risk 41.

**The ownership restart is announced (T-08-63).** The first deploy of an adopted stack adds Bayplan's labels and so recreates what carries them. The review says *N services will be recreated to take Bayplan ownership labels (brief restart)* in a group of its own, apart from real changes, and the Overview says it before anyone presses anything. The classification as ownership-only holds only when every changed path is a Bayplan label (T-08-55). Networks and volumes the stack owns are reused and never created or removed by that deploy (T-08-61); existing secrets and configs are referenced as external and never read, changed or removed (T-08-62).

**A standalone volume is never recreated (T-08-26, T-08-43, T-08-65, T-08-91).** Docker Compose asks *Recreate (data will be lost)?* when a named volume's configuration differs from the file. The engine's prompt is answered **no** in every standalone deploy (Phase 7 stacks too), so a changed volume setting is left alone and the data stays. Adoption goes further: each existing network and volume is written in the form whose configuration hash, computed by the Compose engine's own functions, equals the hash on the host, or is kept `external`, so the first deploy has nothing to recreate. A real-engine test with a marker file in a volume proved the data survives the first deploy of a project made by the real Compose CLI, on Engine 29 (Compose 5.5.1) and Engine 24 (Compose 2.29.1). A network whose settings differ is still recreated, which restarts its containers and loses no data (residual risk 48), and the review now says so for every standalone stack (T-08-64).

**Drift is a read, with bounded cost (T-08-71 to T-08-79, T-08-88).** The drift check, in the background and on demand, only reads the engine: the worker has no write path, and the tests assert the engine's writes are unchanged after a check, a restore review and an accept (T-08-72, T-08-74, T-08-77). The cost is bounded: events are debounced per stack, nothing is checked while the environment's operation lock is held, one check runs at a time per environment, a timed check whose services have not moved skips the diff, a person may have two fresh checks at once (`check_busy`), and one shared read serves the callers of a stack (T-08-71, T-08-75). An event only schedules a check of a stack the environment already has, so a forged or odd event costs one read (residual risk 46, T-08-76). The cause line is built from the audit log with only the action, the actor's display name, the time and replica counts; no address, user agent or other detail leaves it, and the read is bounded to five pages of one environment (T-08-78, T-08-79). The review's **Reverts drift** section runs one more read of the same data and shows the same masked values as the review's current column (T-08-87).

**Accepting live state writes values into the draft (T-08-83 to T-08-86).** The rebuild runs on top of the deployed revision, so stack-made secrets and configs stay declared as files, an environment value equal to a secret variable's is written `${NAME}` and an image keeps the text it was written with: no secret variable's value is copied into `compose.yaml` (T-08-83). It needs `stacks.update`, the same as saving the draft (T-08-85), refuses if the draft changed under the person (`draft_conflict`) and asks before replacing a draft that holds changes (T-08-84), and is audited as `stack.drift_accepted` (T-08-86). **It reveals:** a live value that is not a secret variable's, for example a key somebody set by hand on a service, is written into the draft as it is. Residual risk 41 covers it.

**Names cannot inject (T-08-36, T-08-94, T-08-95).** One rule decides a stack's name for creating and for adopting: letters, numbers, dash and underscore, starting with a letter or number, no dot, at most 61 characters on a swarm and 255 on a standalone host, so a name cannot carry a path, a label filter, a URL fragment or a swarm object name swarm would refuse. A service or network name that swarm would refuse (`{stack}_{key}` over 63 characters, a dot) is a check error before any engine call, and on a swarm two names that differ only in case are one name (409 `stack_name_taken` for creating, 409 `stack_already_managed` for adopting or checking the adoption of an outside `Foo` beside a managed `foo`). Such an outside stack stays in the lists, read-only, with the reason, and is never offered for adoption.

## What Phase 9 adds: git-backed stacks

Phase 9 lets a stack follow a folder of a git repository, and lets a git host, a timer and a commit start a deploy. That
is three new ways for something outside Bayplan to cause a change on your hosts: the repository's content, a request
to the webhook address, and the server's own connection to a git server whose address a person typed. This section says
how each is fenced and where the mitigation is tested. The risks that remain are residual risks 49 to 55.

**The webhook is an unauthenticated route that can start work, and so is treated as a remote-code-execution channel
(T-09-69 and the webhook plans).** `POST /hooks/git/{token}` needs no session, so the request proves itself. The route can
do exactly one thing: ask for a fetch and a check of one stack. It decodes nothing it is sent, takes no ref and no commit
from the body, and cannot deploy by itself; the check fetches the stack's own ref. Whether a check then deploys is the
separate, opt-in auto-deploy setting, judged on the owner's authority (below). The controls are:

- *Two secrets per webhook, both 256 bits from `crypto/rand`.* The routing token is in the address and is stored only as
  its SHA-256; the signing secret is sealed under the stack's ID, so it can be used for HMAC but not read back, and the page
  shows only its last four characters. Rotating replaces both at once. (`TestWebhookSecrets`, `TestWebhookRotate`,
  `TestWebhookSummaryHasNoSecret`)
- *The signature is checked per host*: GitHub and Gitea or Forgejo HMAC-SHA256 over the body, GitLab's shared token, or a
  bearer secret or the token itself for a generic webhook. Every comparison is constant time; an empty secret or digest
  never verifies. (`TestVerifyGitHub`, `TestVerifyGitLab`, `TestVerifyGitea`, `TestVerifyGeneric`)
- *No oracle.* An unknown token, a wrong signature and a paused webhook all answer the same empty `404` with nothing
  recorded for the unknown token. (`TestWebhookNoOracle`)
- *Limits.* 60 requests a minute per client address and 10 a minute per webhook, a 5 MiB body cap, and a burst of pushes
  collapses into one check and one trailing check. (`TestWebhookLimits`, `TestWebhookCoalesces`)
- *Nothing in the body is believed.* (`TestWebhookIgnoresPayload`)
- *It runs on its owner's authority.* The webhook is registered to the Admin who set it up; if they no longer hold
  `git.manage`, requests do nothing until it is handed to another Admin. (`TestWebhookOwnerRecheck`)
- *Audit without secrets.* A delivery and a rejected signature on a known webhook are audited with the stack and the host
  flavour, never the address, token, secret or signature. (`TestWebhookAuditAndLogs`) Paths are redacted in the server log.

**A repository address makes the server open a connection, so it is fenced like a registry address (T-09-01).** Only
`https://`, `ssh://` and `git@host:path` addresses are accepted; `http://`, `git://`, `file://`, a bare path, an option
look-alike (a leading `-`), a control character, a query and an embedded user name and password are refused before go-git
sees the address, because go-git would otherwise read the server's own files for a `file://` address and send a token in
clear text over `http://`. (`TestValidateURLRefusesWhatGoGitWouldHappilyOpen`, `TestPlainHTTPAndTheFileAndGitProtocolsAreNeverSpoken`,
`FuzzValidateURL`) Every HTTPS connection dials through the registry egress policy, which refuses link-local, unspecified and
multicast addresses (the cloud metadata services) after DNS has answered, on a redirect as well, and follows at most five
redirects and only to HTTPS. (`TestLsRemoteEgressBlocked`, `TestLsRemoteRefusesAMetadataAddressAndARedirectToOne`) Private and
loopback ranges stay allowed because self-hosted git servers live there; `BAYPLAN_REGISTRY_BLOCK_CIDRS` refuses more. The
certificate is always verified, with the repository's own CA added for that one call, and there is no option to skip it
(`TestNoOptionSkipsCertificateVerification`). A repository test is limited to 10 a minute per person
(`TestTheEleventhGitTestInAMinuteIsRateLimited`) and a response to 1 GiB, and a fetch has a 10-minute deadline.

**SSH host keys are trusted on first use, by a person (D-03).** Bayplan pins the keys of github.com, gitlab.com and
bitbucket.org. For any other host the first test shows a fingerprint and an Admin confirms it; a later difference is a
hard error and re-trusting is an audited Admin action. The check runs during the key exchange, before any credential is
sent, so an untrusted or changed server never receives one. Bayplan never reads the server user's `known_hosts` or
`ssh_config`. (`TestSSHTrustOnFirstUseStopsAtTheHandshake`, `TestSSHNeverReadsTheServersKnownHostsOrConfig`,
`TestGitSSHChangedKeyStops`, `TestGitSSHRetrustNeedsGitManageOrGitInstance`) The SSH egress check is a little weaker than
the HTTPS one, and that is residual risk 50. Bayplan opens the ssh connection itself (go-git is handed a dialer for the
call), so the connect goes through the egress policy, a server that stalls the handshake is cut off at a deadline and
when the call's context ends, and what a server may send over ssh is counted like what it may send over https.
(`TestSSHHandshakeHasADeadlineOfItsOwn`, `TestSSHFetchStuckInTheHandshakeDoesNotKeepTheMirrorLocked`,
`TestSSHListingStopsAtItsLimit`, `TestSSHFetchStopsAtItsLimit`)

**Credentials are sealed, never echoed and never in an error (T-09-92).** A token or a private key is sealed under the
credential's ID, opened in memory for one call and never put in a response, log or audit row; a mirror holds neither the
address nor the credential. The formatting of the credential types is redacted. Every go-git, TLS and network error leaves
the git package as one fixed code and the host, never its text, because that text can carry an address, a token or a
response body. (`TestSSHCredentialBodyHasNoKey`, `TestGitConnAudit`, `TestClassifyNeverCopiesTheErrorText`) The credentials
travel in a backup only as ciphertext, re-wrapped under the backup's key. (`TestBackupRestoreGitState`)

**Repository content is hostile input (D-10, D-26, D-27).** Bayplan reads a commit from the object database of a bare
mirror by its ID and never checks anything out, so a hostile file name or link cannot write outside a directory. Only
the files the compose files reference are imported, confined to the stack folder; a symlink that leaves the folder, an
absolute path or `..` is refused, and a symlink inside it is read as the file it names. A submodule or a Git LFS pointer
that a stack needs is a blocking problem, so a pointer file is never deployed as if it were the content. `include` and
`extends` are blocked, so a repository cannot pull in a second file from elsewhere. The stack limits apply (50 files, 1 MiB
each, 8 MiB in all) and the folder walk gives up at 100,000 entries. (`TestReadFolderSymlinks`, `TestReadFolderLimits`,
`TestGitLintLFSPointer`, `TestSubmoduleProblem`, `TestSymlinkOutsideProblem`, `TestAMirrorIDThatIsNotAUUIDIsRefused`) A mirror's
directory is named by a repository's UUID, never by anything typed. Commit subjects and author names shown in the interface
are cut to 200 characters and rendered as text.

**An automatic deploy of a hostile commit is limited to what its owner could do by hand (T-09-77, T-09-99).** Auto-deploy
is off by default and opt-in per stack. A deploy it starts passes the same lint, rendering, host-access policy and pin
rules as a person's, as the owner's own principal: an Operator's auto-deploy cannot deploy a bind mount, a privileged
service or the host network, and a stack that used host access makes the owner hold Admin from then on. The owner's
rights are rechecked before every run, and it pauses when they are lost. A commit that fails any check is held back and
shown as an error, not retried in a loop; unreviewed local edits are never deployed over; and a roll back pauses it.
Everything it does is audited with the commit, the trigger, the owner and what it put back. A commit that is *valid* but
harmful (a different image, a command) is not caught, which is residual risk 52. (`TestAutoDeployBlockedPolicy`,
`TestAutoDeployOwnerLostPermission`, `TestAutoDeployNeedsEnvAdmin`, `TestAutoDeployDraftPending`, `TestAutoDeployWebhookActor`,
`TestAutoDeployRevertsDrift`, `TestGitRollbackKeepsSettings`)

**Instance credentials are shared with every environment Admin (D-02).** An instance credential can be picked by a
repository of any environment, so every Admin of every environment can aim it at an address of their choosing, and the
server will send that credential to it. The credential is never shown to them, and a repository that moves to another host must
choose its credential again (`credential_reselect`), but nothing ties a credential to a host. Create instance credentials
that are **read-only deploy tokens or read-only deploy keys limited to the repositories they need**, and use an
environment-level credential when only that environment's Admins should hold it. This is residual risk 49.

**Secret-looking values in a committed `.env` are in the repository already.** A key whose name has a `PASSWORD`, `TOKEN`,
`SECRET`, `KEY` or similar part raises a warning, names the key and not its value, and the value is masked in responses;
a secret variable overrides it. Bayplan cannot make a committed secret safe, only say so (residual risk 53).
(`TestGitLintCheckReportsAMissingRepoFileOnce`, `TestGitLintOverlayClash`, the `env_secret_like` cases of `stackdraft_git_test.go`)

**Mirrors are a cache with a bound.** Untrusted repository objects are stored under `/data/git` (mode `0700`, one bare
repository per saved repository). A repository's mirror is removed when the repository is deleted, and a daily sweep
removes one that is unused for 14 days or over 2 GiB (T-09-91). A mirror records a digest of the address, certificate
authority and sign-in identity (user name, or the deploy key's public key) it was filled from, and a fetch from another
origin starts it again empty, so a repository pointed at another address cannot answer a pinned commit from the old one
(`TestFetchFromAnotherOriginStartsTheMirrorAgain`). Only a rotated secret of the same user or key keeps the mirror. A fetch
waits for a mirror no longer than its context, and a mirror that cannot be had is not a reason for the next fetch, read or
removal to hang. There is no ceiling on the size of a mirror while a fetch fills it other than the bytes one fetch may read
(1 GiB a response over https, 1 GiB over ssh); the sweep trims it after. Losing a mirror loses nothing, because every check
fetches before it reads and a roll back is made from stored revisions. (`TestMirrorGC`, `TestRunMirrorGCLoop`,
`TestRepoDeleteRemovesMirror`, `TestRollbackWithoutMirror`) The mirrors are not in a backup (T-09-92).

**The git tables are in the backup, the derived state is not.** `git_credentials`, `git_repos` and `stack_git` are
included, with their sealed values re-wrapped under the backup's key on restore; `stack_git_state` is derived, so every
git stack starts *unknown* on a restored instance and is checked again. (`TestBackupRestoreGitState`)

## Residual risks

These are known, accepted, and not hidden. 1 to 9 date from Phase 1, 10 to 17 from Phase 2 and 18 to 24 from Phase 3. Residual risk 10 was rewritten in Phase 4 for logs and shells, and 25 to 29 are new in Phase 4, 30 is new in Phase 5, 31 to 36 are new in Phase 6, 37 to 44 are new in Phase 7, and 45 to 48 are new in Phase 8, and 49 to 55 are new in Phase 9 (risk 41 is extended).

1. **Audit tail truncation is undetectable without an external anchor (T-01-26).** The HMAC chain proves that entries were not edited or removed from the middle. Someone who can write to the database can delete only the newest entries, which leaves a valid, shorter chain, and `bayplan audit verify` will still pass. Detecting that needs the head of the chain recorded somewhere an attacker with the volume cannot reach, such as a SIEM; streaming the log out is deferred.
2. **The setup token is visible to anyone who can read the container log or `/data` until setup completes (T-01-37).** It is printed and written to `/data/setup-token` (mode 0600, deleted at completion) by design, so that you can claim the instance without a prior secret. Anyone who has log or volume access already has host admin, but a shared log pipeline can widen that audience. Claim the instance as soon as it starts.
3. **Plain HTTP exposes credentials (T-01-110).** Bayplan serves HTTP unless you configure TLS or a TLS-terminating proxy, and it warns when it does. Passwords and session cookies then cross the network in clear text. First-class reverse-proxy support is planned for a later phase; this build supports `BAYPLAN_TRUSTED_PROXIES` and an `https://` public URL.
4. **The master key sits on the data volume, so a backup of the volume holds both the key and the data it protects.** Encryption at rest therefore defends against a copy of the database file alone, not against a copy of the whole volume. Keep backups protected, or supply the key through `BAYPLAN_ENCRYPTION_KEY_FILE` from a separate store and back it up separately. Losing the key loses the stored secrets and the ability to verify the audit log (T-01-119).
5. **Everything an admin can do, an attacker with an admin session can do (the headline).** Phase 3 narrows who is an admin: an instance admin, or an Admin on one environment, and Operators and Viewers can do less. But an instance admin, and an environment Admin on that environment's hosts, still holds root-equivalent control there, and there is no second factor. Bayplan limits damage with short idle timeouts, lockout and an audit trail; it cannot make an admin session less powerful than the socket it holds.
6. **Single-instance by design.** There is one SQLite writer and no high availability. A compromised or lost instance is recovered from backups.
7. **Inline styles are allowed by the CSP (T-01-63).** A style-injection bug would be easier to exploit than under a fully strict policy. Script injection stays blocked.
8. **Audit growth from scanners (T-01-35) and large exports (T-01-100)** are accepted: every denied read is audited, retention bounds the size, and exports stream from a read connection in batches. Repeated anonymous refusals from one address (denied routes, setup attempts after setup, rate-limited sign-ins) are written individually up to a per-address budget, 20 at once and then 10 a minute, and the rest as one summary entry per minute with a count, so a flood cannot starve the single database writer and every refusal is still recorded. Failed sign-ins that reach the account checks and wrong setup tokens are always written one row each.
9. **The CI end-to-end job runs a privileged Docker-in-Docker container (T-01-115)** on an ephemeral hosted runner with no secrets.
10. **A compromised Bayplan can do everything an agent's route table forwards, on every host whose agent is not read-only.** It can read the container, image, volume and network lists, the swarm's nodes, services and tasks, the events stream, any container's logs, and the **inspect of any single container, which includes that container's environment variables**. Bayplan masks those values for users without `secrets.reveal`, but the agent forwards the whole answer, so a secret passed to a container as an environment variable can be read through an agent. It can stop, kill and remove containers (and their anonymous volumes), and create and delete networks and volumes. It can **open a shell in any running container, as any user the image has, root included** (the agent refuses a privileged exec, but not a root user), and a shell in a container that is privileged, mounts the Docker socket or mounts the host's file system is root on the host. It can create a `local` volume that binds a host directory under `/srv`, `/mnt` or `/media`, or anywhere on a host whose owner opted in (T-04-10, T-06-119), and a service it creates, or a container someone else starts, with that volume sees the host path. It can **make any node pull any image**, which runs nothing by itself but fills the disk and lets a later container start from an image the attacker chose, and it can **present a stored registry credential to that registry** by pulling from it; it can remove an image that no container uses. Pulls and removes are refused on a read-only host. Residual risk: **a compromised node learns the credential of every image pulled on it**, because Docker needs the credential on the node to authenticate to the registry; this is inherent to registry authentication, so give Bayplan least-privilege, read-only registry tokens. **On a swarm manager whose agent is not read-only it can also create, change and remove services** (Phase 6): it can start any image as a service on the swarm, with any command, environment, secret and config reference, network and placement, and remove any service. **Without host access**, which is what the agent enforces unless the host opted in (`BAYPLAN_AGENT_ALLOW_PRIVILEGED_SERVICES=true`), such a service cannot bind the Docker socket or a host path outside `/srv`, `/mnt` and `/media`, add a capability, lower its sandbox or join the host network, but it can still run arbitrary code in a container on every node, reach whatever the swarm's networks reach and read the secrets and configs it is given. **With the opt-in it can run a privileged service on every node, which is root on every node**, so enable it only on a swarm where you accept that. A consequence of the same check is that on a host without the opt-in Bayplan cannot change a service that already has host access (every update carries the whole spec). **On a swarm manager it can also change nodes and swarm objects** (Phase 6): update any node's availability, role (promote and demote) and labels, which steers where every service runs and can cost the swarm its quorum; remove a node that Docker reports as down, though never one that is up, because the agent has no `force` key to send; create and delete secrets and configs (a delete is refused by Docker while a service uses it); read the **content of every config** and the metadata of every secret, though never a secret's value; follow the logs of any service or task; and sample the CPU, memory, network and disk counters of any container. Set `BAYPLAN_AGENT_READ_ONLY=true` to refuse all the writes on a swarm Bayplan should only watch. It cannot create or change a container directly, build, import or push images, read a container's files, or read the swarm join tokens through an agent, and it can ask an agent to update or uninstall itself, with the limits above. Set `BAYPLAN_AGENT_READ_ONLY=true` on hosts Bayplan should only watch, avoid privileged and socket-mounting containers on managed hosts where you can, treat the Bayplan server as holding the inventory and the shells of every host, and prefer Docker secrets to environment variables for what you run.
11. **The standalone join token stays in `docker inspect` until it is rotated.** Once the agent has enrolled the token is not needed again; rotating it in Bayplan and recreating the container with the new command removes the exposure. A swarm keeps the token in a Docker secret instead.
12. **A broken agent image can leave one node's agent down.** A swarm rolls with Docker's own rolling update, whose default on failure is to pause: a bad image stops the first node's agent and leaves the rest on the old one until an operator runs `docker service rollback`. Bayplan shows the node as disconnected and, after fifteen minutes, the failed update. Releases are signed and pass the end-to-end run first (see the release checklist), which keeps the chance low, not zero.
13. **The agent's address changes only by pushing a new address to connected agents or by reinstalling.** The server accepts one audience, so an agent that dials a host or port that is no longer the configured one is refused, including one that was offline during the change. For 0.x this is decided (option B, 2026-10-04): Bayplan does not accept the previous address for a fallback period, because a second accepted audience widens what a handshake addressed elsewhere can be replayed against. The Settings confirmation and `docs/agent.md` say so.
14. **A leaked agent key is valid until its certificate lapses or an admin revokes the node.** Revoking is immediate, and an admin revoke also blocks the node from enrolling again, but there is no revocation list for a certificate that Bayplan itself has not seen used.
15. **Agents can be cloned.** A virtual machine copied from another shares its Docker engine ID, so Bayplan refuses it as a duplicate until the engine gets a new identity (see `docs/agent.md`). A node that is not refused for that reason, but shares an agent state volume with another, would share its key; keep the `bayplan-agent` volume per host.
16. **A flood of silent handshakes from four or more addresses can still fill the 64 slots (T-02-128).** One address, or one IPv6 /64, holds at most 16, so four are enough (4 x 16 = 64). Each slot is freed after 3 seconds, so the flood must open a new connection every 3 seconds per slot to keep it up. Connected agents are unaffected, and an agent that is refused waits and tries again.
17. **A loopback agent address admits plain connections from any peer (T-02-141).** When the agent address is on Bayplan's own machine, Bayplan accepts plain connections from any peer, because it judges the address agents dial and not the peer (a containerised Bayplan sees its local agent through the bridge gateway). An agent told to dial loopback sends nothing over a network, and a remote caller exposes only what it sends. Every agent still has to authenticate.
18. **The count of repeated refusals is lost on a hard kill.** The first refusal of each kind is always written in full and at once. The counter of repeats inside the open 60-second window lives in memory and is written when the window closes or at a clean shutdown, so a power loss or `kill -9` loses the count, not the refusal.
19. **File locks on network file systems.** `bayplan restore` and `bayplan key rotate` refuse to run while a server holds the data-directory lock, but a file lock is advisory and some network file systems (NFS, some FUSE mounts) do not honour it. Do not keep `/data` on one, or stop Bayplan yourself before running either command. Running either against a live server can corrupt the database.
20. **Administrators' usernames are shown to a user with no access.** The page for a signed-in user who can see no environment lists the usernames of the instance admins, so they know whom to ask. Any account, including a freshly invited one, can read them. Usernames are not secret in Bayplan, but they are a small disclosure.
21. **The scheduled backup's passphrase is readable by anyone who holds `/data` and the master key.** It must be stored to run unattended, sealed under the master key. Someone with a copy of the volume (which holds the key unless you supply it separately) can read it and open the backups made with it. Supply `BAYPLAN_ENCRYPTION_KEY` from a store apart from the volume, keep scheduled backups on a different volume, and use a passphrase that is used nowhere else.
22. **`unknown_agent` tells whoever holds an agent's key and certificate that the agent is unknown.** After a restore, an agent enrolled after the backup is refused with that reason, and the reason names a state of the database. Bayplan says it only after the signature checks out against the certificate's own key, so a copied or forged certificate learns nothing, and the answer is the same for every such agent. But it is more than the generic refusal a stranger gets.
23. **A leaked invite or reset link can be used by anyone until it is used, replaced or expires.** It is a bearer token, 72 hours by default. Bayplan sends no email, so the admin must pass it on privately, and a link pasted into a chat or a ticket stays readable there. Shorten `BAYPLAN_INVITE_TTL`, and regenerate a link you doubt.
24. **A backup file and its passphrase together are the whole instance.** A backup holds password hashes, the environments' certificate authorities and the full audit log. Anyone who can open it can sign in as any user after restoring it somewhere, and can issue certificates that the environments' agents accept. A weak or reused passphrase makes the argon2id cost irrelevant. Store the file and the passphrase apart, and treat both like the data volume.
25. **A process started in a browser shell can keep running after the shell is closed (T-04-80, accepted; D-30).** Closing the tab, losing the connection or an idle or administrator end closes the terminal, and Docker does not end a process that ignores the hang-up, so a daemon or a program started with `nohup` stays in the container. Bayplan does not search for or kill what is left, and the `shell.closed` row records that the process was still running. This is described under the audit of shells above; `docs/containers.md` says how to check (`docker top`, `docker exec <container> ps`) and stop it.
26. **Everyone who can read a container's logs sees whatever the application prints (T-04-63, accepted; D-23).** Logs are shown exactly as written and are never masked, and a Viewer can read them. An application that logs a password, a token or personal data shows it to every Viewer on that environment, and a downloaded log leaves Bayplan as a file. Only the opening and the download are audited, never the lines. Fix it in the application, or keep people who should not see it off that environment. `docs/containers.md` says so.
27. **Labels, and the driver options of networks, are shown as Docker reports them (T-04-41, T-04-30, accepted).** The container page and its Inspect JSON show every label to anyone who can read the container, the network and volume pages show their labels, the network's Inspect JSON carries its driver options, and the container search matches label values on the server, so a label value can be found by searching for it. The values of environment variables, log-driver options, the command line and volume options are masked (see "Values that can hold credentials" above), but a label is not, and neither is a container's start error, which Docker sometimes writes with the command in it. Do not put a secret in a label or a network option.
28. **An environment Admin can create a volume that binds a host directory, and a service or container that someone else starts can then see that directory (T-04-10, T-04-56, T-06-122, accepted).** The directory is under `/srv`, `/mnt` or `/media`, or anywhere on a host whose owner opted in or on the server's own host (local socket, no agent). This is described in residual risk 10. The volume's options, including the path, are in the audit log.
29. **A volume create's audit row masks options by name (fixed list, accepted).** The row hides the value of any option whose name says it is a password, secret, credential, token, key, auth setting, private key, certificate or identity, and any user and password in a URL. A plugin volume driver that takes a secret under another name would have it recorded in the audit log, up to 500 bytes. Treat the audit log of an environment with such drivers as holding their options.
30. **A credential with the insecure switch on can be read, and its answers forged, by anyone on the network path (T-05-40, accepted).** When an operator turns on "Allow plain HTTP or skip TLS verification" for a credential, Bayplan's own tests and tag browsing for that registry no longer check who they are talking to, and the sign-in is sent in clear text if the registry answers plain HTTP. The switch is off by default, is per credential, is warned about in the sheet and is recorded in the audit rows of the credential and of each test. It affects only calls the Bayplan server makes; it does not change a node. Use it only on a network you trust, or give the registry a certificate and add its CA to the credential instead.
31. **A secret value passes through Bayplan's memory once (T-06-65, accepted).** A create carries the value as base64 in a request body. The server decodes it, forwards it and clears its own copy of the decoded bytes, but the request body, the base64 string and the HTTP buffers are Go memory that is freed by the garbage collector, not wiped, so someone who can read the server process's memory while a create runs, or soon after, could find it. The value is never written to the database, the log, the audit log or a cache, and a backup does not hold it. Docker keeps secrets encrypted in the swarm's raft log.
32. **Config content and service labels are readable by everyone who can see them (T-06-71, T-06-72, accepted).** Docker returns a swarm config's content with every list and inspect and does not encrypt it, and Bayplan shows it on the config's page and in its Inspect document to every Viewer on the environment (`configs.read`). A service's labels, and the labels of nodes, secrets and configs, are shown as Docker reports them and are matched by the search on the server, as a container's are (risk 27). The values of a service's environment variables, command, arguments, health check test and log-driver options are masked; its labels and its configs are not. Put credentials in a secret, never in a config or a label, and do not give people read access to an environment whose configs or labels you would not show them. `docs/services.md` says so.
33. **With `BAYPLAN_AGENT_ALLOW_PRIVILEGED_SERVICES=true`, a compromised Bayplan can run a privileged service on every node (T-06-07 to T-06-10, accepted, host owner's choice).** The opt-in lifts the agent's host-policy check for every manager of that swarm, and the only remaining limits are Bayplan's own, which a compromised server does not honour. The opt-in also lets a compromised Bayplan, on every agent-managed host, create volumes that mount the host or use a plugin, and on a manager mount such a volume, a plugin volume or a cluster volume in a service. A service that binds the Docker socket or `/` is root on every node it is scheduled to, so the headline holds in full for that swarm. Leave the variable off unless a service you run needs host access, and then weigh turning it back off. Without it, Bayplan cannot change a service that already has host access, scale, force update and roll back included; that is the price of the check, and `docs/services.md` explains it to users.
34. **Everyone who can read a service's logs sees whatever its tasks print, and the merged order is approximate (T-06-85 to T-06-88, accepted).** Service logs are shown as written, never masked, to every Viewer of the environment, and a downloaded file leaves Bayplan (risk 26 applies in full). Only the opening and the download are audited, never the lines. The merge puts lines from different nodes in time order in a short buffer, so nodes with unsynchronised clocks, or a line that arrives after its neighbours were sent, can show out of order; the file a download writes is ordered after the whole range has been read.
35. **The agent cannot judge what a rollback restores, or a volume it cannot see (T-06-116, T-06-123, accepted).** The agent sees only the current spec of a `rollback=previous` update, so on a host without the opt-in a compromised Bayplan could restore a previous spec with host access. Such a spec exists only if one was live before, because it was applied while the host had opted in or was made outside Bayplan. A manager's agent inspects a named volume on its own engine only, so a volume of the same name with host access that exists only on another node is mounted when a task lands there, whether it was made outside Bayplan, made through Bayplan while that node's agent had the opt-in, or made through Bayplan before this agent release (agents before plan 06-50 also forwarded a volume that binds a relative device or mounts another filesystem type). After turning the opt-in off, update such services twice (so their previous spec has no host access) and, on every agent-managed host, list the volumes, inspect each and remove the ones that bind a relative path or a host path outside `/srv`, `/mnt` and `/media`, mount a filesystem type other than `tmpfs` or a network share, or use a plugin. This clean-up advice is untested.
36. **Changing a service's settings exposes what that service holds (T-06-140, accepted).** Whoever holds `services.control` on an environment can change what a standalone service runs (its image, command, environment variables, mounts and configs), so they can read the values Bayplan withholds from them on that service (its environment values, command line, health check and log options) and the secrets it already uses, without `secrets.reveal`. Masking stops a reader, not an editor. Adding a secret the service does not already use, or bringing one back with a rollback, needs `secrets.reveal` (plans 06-47 and 06-48), and the server matches a secret by the engine's secret ID and refuses a reference whose name is not that of the secret its ID points at (plans 06-52 and 06-53), so an editor cannot reach a secret that no service they can edit already uses, and stack-owned services cannot be edited from the service pages (D-05). A service spec saved before this release with such a reference still mounts the secret its ID names. Bayplan refuses a review, an apply or a rotate's update that would send such a reference, and a rollback to a previous spec that has one, until the name is corrected; a rotate of the secret its ID names replaces the reference with the new version's ID and name. A scale or a force update re-sends the stored spec as it is, with the same IDs, and adds no reference (T-06-151). Give `services.control` only to people you would trust with those values, and do not mount secrets into standalone services that people below Admin edit unless they may read them.
37. **The hash in a secret's name is not secret (plan 07-07, accepted).** A swarm secret or config made from a stack file is named `<stack>_<name>_<hash>` and carries the hash in the `bayplan.stack.object.hash` label, and a standalone container carries the hash of each secret and config it uses in a `bayplan.stack.secret.<name>` or `bayplan.stack.config.<name>` label. The hash is the first 8 hex digits (32 bits) of a SHA-256 over the name and the content, with no key, and the names and labels are readable by everyone who can read services, containers, secrets and configs (risk 27, risk 32). It narrows what the secret can be, and for a low-entropy secret (a short PIN, a dictionary word) a guess that matches is nearly a confirmation. It is a version marker and not a protection: use secrets with real entropy (a random key or token), never a word.
38. **A compromised agent or engine chooses the text a deploy console shows (T-07-82, accepted).** The console shows Docker's own words under a failed service (task errors, pull errors, a rejection), and the engine, or an agent that forwards a forged answer, decides them. Bayplan removes control characters, keeps at most 2,048 characters and draws every such string as text, never markup, so it cannot run script, but it can mislead: a message can tell the reader to do something. Treat a surprising instruction in a deploy failure like one in any log.
39. **The Compose engine brings a large dependency tree into the server (T-07-96, T-07-99, accepted).** Deploying a standalone stack with Docker's own Compose engine pulls in its dependencies (build, container runtime and telemetry libraries) beyond what the rest of Bayplan uses, so the server binary is larger and a flaw in any of them is a flaw in the server. The versions are pinned, the licence check runs over them, only `internal/dockerx` may import the engine (a lint rule), its client is guarded method by method, and the features that would make it run a program on the server are refused. The tree is still the widest dependency surface Bayplan has: keep the server image up to date.
40. **Two host-access gaps are open decisions (T-07-66, accepted until decided).** `sysctls` and `ulimits` are not in the rule set of the compose policy, the service policy or the agent, so an Operator can set them in a stack and, since Phase 6, on a service. And a `service:X` network, IPC or PID namespace and `volumes_from` are not host access to the manager's rules, so an Operator can deploy and review such a stack, but a host's agent refuses it as host access unless the host owner opted in (it works on the Bayplan server's own host, which has no agent). Neither is hidden by the review.
41. **Masking hides the values Bayplan knows, from readers, and stops no one who writes the stack (T-07-141, T-07-46, accepted).** The masker removes the stack's secret variables and secret files of 4 characters or more from reviews, the console and logs. It does not know a secret an application makes up, a value a container prints in another form (encoded, split or reversed), a value shorter than 4 characters, or a secret changed after a log was opened (until it is opened again). A value in a running service that did not come from the stack, set with `docker service update`, is shown unmasked in the review's *current* column to whoever holds `stacks.deploy`. And **whoever may deploy a stack may write a compose file that prints its own secrets**: an Operator who can deploy can read the secrets the stack's services use, as risk 36 says for services. `secrets.reveal` governs reading a value in Bayplan, not what a deployed container can do with it. **Phase 8 adds three more places where a value the masker does not know is readable by `stacks.read` holders (T-08-08, T-08-50, T-08-87, T-08-92, D-15, D-47, D-54).** (a) **An adopted stack's draft holds the services' environment values as literals.** Adoption copies them as they run, passwords and tokens included, because Bayplan cannot tell which are secret, and the masker knows only the stack's own secret variables. Anyone who can read the stack's draft (every Viewer of the environment) can read them in the Editor. (b) **So can they in History.** Revision #1 of an adopted stack stores a rendering with the same literals, and History's *Rendered* and *YAML diff* views show a stored rendering to every `stacks.read` holder; a later revision keeps whatever the draft held when it was deployed. Moving a value to a secret variable hides it from then on, but **it stays readable in revision #1 and every older revision that holds it until pruning deletes that revision** (retention, residual risk 45). The adopter is an environment Admin and so holds `secrets.reveal` by default, which is why the adopt page says in so many words that environment values are copied as they are and to move secret ones to Variables. (c) **Accept live into draft writes into the draft any live value that is not a secret variable's.** It rebuilds with the values revealed, for the person with `stacks.update`, so a key somebody set by hand on a service, or any value a service holds that no secret variable of the stack equals, lands in the draft where every `stacks.read` holder can read it. A value that equals a secret variable's is written `${NAME}` (T-08-83), so the stack's secrets do not leak this way. (d) The review's **Reverts drift** section shows the live value of a setting it would put back to a `stacks.deploy` holder, masked by the review's masker, so a hand-set secret the masker does not know is shown, as in the current column. What is hidden for callers without `secrets.reveal` is the preview, the adopt check, a revision's Changes and the drift view (see "What Phase 8 adds"), not the stored definition. Put secrets in secret variables and files, and move them there right after adopting.
42. **A tag the registry moved is not pulled, but an image the pin guard cannot judge is (T-07-43, accepted).** A service whose image text is unchanged keeps its digest, so a moved tag never changes what runs. Two cases weaken the picture. On Docker Engine 29 the containerd image store lists a repository digest for every image, so Bayplan cannot take an image that exists only on the host for a local one, and a deploy of it stops at the lookup instead of pinning the image ID; relaxing the rule would lose the guard against silently pinning a stale local copy. And a standalone service with `pull_policy: always`, `daily` or `weekly` makes the Compose engine pull again, anonymously, after Bayplan pulled with the stored credential: a pinned digest keeps it from moving to a newer image, but a private image fails there.
43. **A compromised Bayplan can write one ordinary file into a stopped compose container on a managed host (T-07-16, T-07-19, accepted).** The agent's archive route exists so the Compose engine can write a secret or config into a container before it starts. It accepts one regular file (a clean name, no setuid, setgid or sticky bit, no link, device or extended record, at most 1,000 KB) at the root of a container that carries the `com.docker.compose.project` label and is not running, and a compromised server can create such a container (within the container rules, with no host access) and write a file into it. That is what a stack's own secret does, so it is no new reach, but the not-running rule is a guard against a general live-write route and not a boundary against a compromised server, which can stop a container first. The agent's opt-in lifts the container rules as it lifts the service rules (risk 33).
44. **A crafted secret file can make a review spend minutes of CPU (accepted, fix known).** The masker builds a replacer over each secret value, and the standard library's replacer is quadratic for a long value made of one repeated character: a 520,000-byte secret file of one character took about 88 seconds in one review, and a varied file of about a megabyte takes seconds. An Operator can save such a file (they may save drafts), and the review, the console and the logs all build the masker. The fix is a linear masker or a cap on the longest value masked as a whole; until then, restrict who is an Operator on an environment to people who may slow the server, as for any shared resource.
45. **Pruned revisions leave their pages in the database file (T-08-22, accepted).** Deleting a stack's older revisions removes their rows, their files and their variables, including sealed secret variables and secret files, but SQLite does not wipe the freed pages, and `PRAGMA secure_delete` is not set. What was sealed is AES-GCM ciphertext under the master key, so a copy of the database file alone shows nothing new; a copy of the whole volume holds the key as well (risk 4). Plain values and the stored renderings of a pruned revision (risk 41) can remain readable in those pages until they are reused. The retention limit is how long the newest revisions live, and lowering it is irreversible and confirmed in the page.
46. **A forged Docker event costs one read (T-08-76, accepted).** The background drift worker acts on service and container events and schedules a read-only check of a stack the environment has, found by the service's name or the Compose project. A compromised engine or agent that sends events naming stacks can make Bayplan check them, one at a time per environment, after a 3-second quiet period and never while an operation holds the lock. It cannot make the worker write, and it cannot name a stack the environment does not have. The check does read the engine and, for a swarm, the audit log (bounded), so a flood costs CPU on the server, not data.
47. **Everyone who can read stacks sees what is on the environment that Bayplan did not make (T-08-29, T-08-35, accepted).** An unmanaged stack's name, services, images, ports, states and logs are shown to every Viewer of the environment, as the Services and Containers pages already show them, and so is the list of stacks the environment holds. The environment values, commands, health check commands and log options of those services are not (D-47), but its labels, and its logs as written, are (risks 26, 27 and 34 apply). Adopting such a stack with its environment values is risk 41.
48. **The first deploy of an adopted stack restarts it, and a network whose settings differ is recreated (T-08-27, T-08-63, accepted).** Adding Bayplan's labels recreates the services or containers that carry them, which restarts them briefly, and the person who deploys is told how many before they press anything. A standalone network whose settings differ from the file is recreated by the Compose engine, which restarts the containers on it and loses no data; the review of every standalone stack now lists such a network before the deploy. A volume is never recreated, so a change to a volume's settings is not applied (it is left alone and the data stays): a person who needs the change must remove the volume by hand.
49. **An instance git credential can be aimed at any address by any environment Admin (D-02, accepted).** An environment's repository may pick an instance credential, nothing ties a credential to a host, and the server sends the credential to whatever address the repository has. An Admin of any environment can therefore make Bayplan send an instance token to a server they run (the credential is never shown to them, and moving an existing repository to another host forces a new choice, but a new repository has no such check). Give instance credentials the least access that works: a **read-only** deploy token or deploy key, limited to the repositories it must read, and prefer an environment credential when only that environment needs it. Anyone who can create a repository with it can also read what it can read.
50. **The SSH connection is fenced at connect time, but the name is resolved twice (accepted; same family as WR-B02).** Bayplan opens the ssh connection itself, through the egress policy's dial hook, so the address actually connected to is checked before any byte is sent, and no proxy of the server's environment (`ALL_PROXY`) is used. It also resolves the host first and refuses an address the policy blocks before it dials; that early lookup is a second, separate resolution, so a name that answers differently each time can pass the early check and is then judged by the dial-time one, which is the one that counts. The handshake has a 15 second deadline, a listing may read 32 MiB and a fetch 1 GiB over ssh. Use https addresses where a host's address policy matters.
51. **The webhook receiver is rate limited by client address, and a flood can lock out deliveries (accepted).** The per-address limiter fails closed when its table of 65,536 addresses is full, so a flood from very many addresses could stop webhook deliveries until it empties; polling still finds the push. Behind a reverse proxy without `BAYPLAN_TRUSTED_PROXIES` every delivery appears to come from the proxy and shares one budget of 60 a minute. Every check that runs apart from its caller (a poll's, a webhook's, and the automatic deploy that follows) is ended and waited for when the server closes, before the jobs and the database close; the wait is capped at 15 seconds, and a call that ignores its cancellation past that is left to end with the process. Someone who holds a webhook's address and secret can make Bayplan fetch, at most 10 times a minute.
52. **Whoever can push to the followed ref can change what runs, and auto-deploy does it without a review (accepted, by design).** Bayplan's checks catch a commit that breaks a rule (host access, a missing variable, a clash), not one that is valid and harmful: a different image, a changed command, a new port. With auto-deploy on, push access to the branch is deploy access, on the authority of the stack's owner. Protect the branch or tag in the git host, leave auto-deploy off for anything you do not want a push to reach at once, and use a fixed commit when you want a human to move it. An automatic deploy also puts back changes made by hand (the repository is the source of truth); it records what it reverted and the bell notes it, but the change is gone.
53. **A secret committed to the repository stays in the repository (accepted).** Bayplan warns when a key of the committed `.env` looks like a secret and a secret variable overrides it, but the value is already in the git history and on the git host, and it is kept as an ordinary file in each revision of the stack. Rotate a value that was committed. Secret file contents belong in overlay files, which are sealed.
54. **The mirrors hold the fetched repository unencrypted on the data volume (accepted).** Under `/data/git` (mode `0700`) sit the git objects of every ref a stack follows, including those of private repositories, in the clear. Anyone who can read the volume reads what the credentials could read; guard the volume as risk 4 says. A mirror is removed with its repository, after 14 days unused or over 2 GiB, and is not in a backup.
55. **A restored instance trusts its git state again only after it checks (accepted).** A backup holds the repositories, credentials and git stacks with their sealed secrets re-wrapped, but not the state of the last check or the mirrors, so each git stack reads *unknown* until its first check, and the host keys a person trusted come back with the repository. The webhook addresses keep working only if the instance's public URL is the same.
